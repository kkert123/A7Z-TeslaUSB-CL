# 2026-11-07

## 诊断：清理耗时 6.5 分钟 + 「清理历史加载失败」

用户报两件事：① 清理历史页报「⚠️ 清理历史加载失败」；② 清理耗时从「以前 1 分钟内」变成 6 分半，
怀疑是最近几天改的代码导致。

### 一、时间到底花在哪（日志时间线，真机取证）

| 时刻 | 事件 |
|---|---|
| 10:23:25 | 第 1 次 `POST /api/cleanup/execute` 开始 |
| 10:23:26 → 10:29:34+ | 持续刷 `ERROR 删除文件失败 ... [Errno 2]`（全是缩略图） |
| 10:30:00 | `清理孤儿缩略图释放: 391.8 MB` + `400.2 MB`（**两行 = 两次运行**） |
| 10:30:01 | `=== 清理执行开始 ===` ×2（视频阶段） |
| 10:30:02 | `=== 清理完成: 删除 1607 个文件, 释放 39.6 GB ===`（两条） |

→ **视频删除只花 1 秒；6 分 35 秒（395 秒）全部耗在「删缩略图」阶段**。

### 二、根因：`_delete_file_safe()` 里的 O(n²)

```python
os.remove(fpath)
parent = os.path.dirname(fpath)
for _ in range(3):
    if os.path.isdir(parent) and not os.listdir(parent):   # ← 每删一个文件就 listdir 整个目录
        os.rmdir(parent)
```

缩略图全部平铺在同一个目录里。真机微基准：

| 目录 | 项数 | `listdir` 单次 |
|---|---|---|
| `shared/thumbnails` | 23,341 | **16.91 ms** |
| `v74/static/thumbnails`（清理后） | 317 | 0.85 ms |

23,341 × 16.91 ms = **395 秒** = 实测 395 秒。**一分不差，O(n²) 实锤。**

### 三、为什么「以前 1 分钟内」——最近改动的触发链

O(n²) 是**老代码**，不是新写的；v0.3.1.74 把它从「无害」变成「爆炸」：

1. v74 `ensure_shared_thumbnails()` 把 **7 个版本目录**的缩略图合并成一份 `shared/thumbnails`
   = 23,341 项（并集，含大量**早已没有对应视频**的历史孤儿，其中 14,911 个 mtime > 7 天）。
   以前每个版本各持一份（14,836 项），每次清理只删**几十个**孤儿 → 几十 × 11ms ≈ 0.5 秒，感知不到。
2. 装 v74 的那次升级由 **v72 的旧代码**执行，旧 `_save_user_data` 的 `copytree` **穿透 symlink**
   把 2.8G / 23,341 个整份复制成 `v74/static/thumbnails` **真实目录**。
3. 于是这次清理一次性看到 **约 23,000 个孤儿缩略图**（全在同一目录）→ n 从「几十」跳到「两万三」→
   O(n²) 立刻显形，395 秒。

**结论：最近改动（v74 缩略图合并）是触发器，老 O(n²) 是放大器。**

### 四、「清理历史加载失败」的根因

`/opt/radxa_data/teslausb/data/cleanup_history.json` 实测损坏：
`JSONDecodeError: Expecting value: line 49 column 226 (char 8200)`。

- **char 8200 = 8192 + 8** → 正好跨过一个 8KB 缓冲区边界 → 典型「写一半被截断」，不是随机损坏。
- 有 **两份** `_save_cleanup_history` 写同一个文件：
  - `auto_cleanup.py:1128`（`open(w)+json.dump`，异常只 log）
  - `routes/cleanup_routes.py:546`（`open(w)+json.dump`，且 `except: pass` **静默吞异常**）
- 两次清理并发 → 两个写者交错 `open(w)` 截断 → 一方 dump 到 8KB 处另一方又 truncate → 断在 8200。
- 读接口 `api_cleanup_history()` 直接 `json.load` → 抛异常 → 500 → 前端「清理历史加载失败」。
- 与 **M114**（`.teslamate_token.json` 被 4 进程非原子写坏）是**同一类缺陷，第二次犯**。

### 五、附带发现

- `/api/cleanup/execute` **无并发保护** → 双击跑两份（同秒两条 200）。
- `_delete_file_safe` 把并发竞态的 ENOENT 记成 `ERROR`（应记 skipped）。
- `shared/thumbnails` 2.8G / 23,341 个**已被孤立**：当前真实用的是 `v74/static/thumbnails`（317 个 / 51M）。
- 前端：执行中按钮不禁用、无进度、无「已用时」提示。

### 六、拟修方案（待用户确认后实施，v0.3.1.75）

P0：
1. **干掉 O(n²)**：父目录回收改 `next(os.scandir(parent), None) is None`（单次 readdir，与目录大小无关），
   并在本轮内缓存「已确认非空的 parent」不再重复查；缩略图阶段（目录是平的）直接跳过父目录回收。
2. **`/api/cleanup/execute` 单飞锁**：`threading.Lock` + `/var/run/cleanup.lock`（PID/开始时间），
   在跑就返回 `409 正在清理中（已进行 Ns）`。
3. **`cleanup_history.json` 原子写 + 坏文件隔离**：两处实现合并为一处；`mkstemp`+`os.replace`；
   读遇损坏隔离为 `.corrupt-<ts>` 后重建，接口返回空列表而非 500；去掉 `except: pass`。

P1：
4. ENOENT → skipped，不再 ERROR。
5. 前端：禁用按钮 + 已用时 + >30s 提示「可能需数分钟，请勿重复点击」。

现场一次性：
6. 修 `cleanup_history.json`（备份损坏件、抢救可解析条目、重建）。
7. 缩略图归一：以 `v74/static/thumbnails` 的 317 个为真相 → 搬入 `shared/thumbnails`、
   清掉 23,024 个陈旧孤儿、建回 symlink，回收约 2.8G。
