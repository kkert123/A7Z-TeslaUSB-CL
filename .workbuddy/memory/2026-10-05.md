**事故经过**：
1. 热部署成功后，**想启用并发开关**：直接写 `config/ap_config.json` 加 `ap_sta_concurrent=true` —— **失败**（该文件 root 属主，radxa 无权写，PermissionError）。此时开关**仍是 false**（`_use_concurrent()` 回退 `config.AP_STA_CONCURRENT_DEFAULT=False`）。
2. 未察觉开关未生效，即调 `POST /api/ap/control {"action":"start"}` → 走 **legacy** `_ap_bring_up`：`nmcli device set wlan0 managed no` + `stop wpa_supplicant` + 起 systemd hostapd（wlan0 独占模式）→ **wlan0 的 STA 被释放 → Tailscale 随 wlan0 断开 → 设备失联**。

**根因（我的操作失误）**：在**未真正启用并发开关**的情况下，对**远程唯一链路（Tailscale 走 wlan0）**发起了会释放 wlan0 的 legacy 起 AP 操作——正是本项目一直对抗的"互斥切换"故障模式。**教训：远程设备上，任何可能释放 wlan0 的动作必须先确认"当前走的是并发路径（wlan0 不受影响）"，否则等于自断链路。且 root 属主配置文件不可由 radxa 直接写。**

**设备当前状态（无法远程确认）**：wlan0 大概率处于 AP 模式（广播 `TeslaUSB-Setup`）或 unmanaged 卡死；Tailscale 不可达。

**恢复预案**：
- **A（最可靠）断电/重启设备**：开机后走 legacy 正常逻辑 → wlan0 连 C12345 → Tailscale 恢复。**新部署代码默认 `ap_sta_concurrent=False`，行为与旧版等价，重启安全**（注：`/tmp/a7z_m2_bak` 会随重启丢失，但无需它——新代码 legacy 路径 == 旧行为）。
