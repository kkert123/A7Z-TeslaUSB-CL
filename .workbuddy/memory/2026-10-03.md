# 2026-10-03 工作日志

## 10-03 生产 Bug：AP 自动开启后不回连 WiFi（根因分析完成，**修复未开始**）

**用户报告**：早上车机热点重启后，设备自动切到 AP 模式，之后不会自己切回 WiFi；必须手动进页面关闭 AP 才能连上 WiFi。

**结论：不是 v0.3.1.59 回归**，是 **v0.3.1.31 起既有设计缺口**被"车机热点重启"场景命中。两条叠加：

- **R1（核心）**：fallback 自动开的 AP 有 **15 分钟「全静默窗口」**（`AP_GRACE_PERIOD_SEC=900`）。窗口内 `full_check` 全量检测（wifi_service.py:2413-2425，v31 注释"降频窗口"）与 `_ap_self_heal()` 让出探测（:2697）**双双 early-return** → 零回连探测。只剩三种出口：①手机连上 AP 再断开→`ap_client_event.sh` 15s→`--yield-ap`（本例走这条：07:35:49 连→07:36:38 让出）②人工关 AP ③干等满 15min。
- **R2（放大器）**：`SWITCH_COOLDOWN_SEC=300` 让 `_switch_to()` 在恢复路径上否决了**唯一可连网络**（YL-MIFI-000500，信号 100%，距上次切换仅 4min）→ `reconnected=False` → "所有网络均无法连接" → 07:29:10 凭空多开一次 AP。

**时间线**（证据：`/var/log/wifi-smart-switch.log` + hostapd/wpa_supplicant journal + teslausb.log，均经 Web API:5000 下载）：
07:02–07:25 车机热点反复不稳(3 次重连) → 07:29:09 尝试连 → **07:29:10 冷却跳过 + 开 AP** → 07:29:55~07:35:21 四轮 full_check 全"降频窗口跳过" → 07:35:49 手机关联 → 07:36:38 hostapd Stopped 回连 → 07:45:06 在家纠正切 C12345 → **07:47:04 用户从页面重启设备**（来源 100.95.159.87）→ 07:49:34 连上 C12345 后全程正常。

**非 v59 回归的证据**：`manual_off_active:false`/`manual_off_remaining:0`；v59 的 transition/manual-off 守卫只挡**开** AP，不挡回连；设备当前 APP_VERSION 仍 0.3.1.58。

**修复方案（已给 A/B/C，待用户确认，未改任何代码）**：
- R1：A（15min 全静默→降频探测窗口，让出探测改由 指数退避+切换冷却+客户端感知 三重限流，全量扫描仍降频）｜B（900→180s 一行）｜C（A+AP 超 N 分钟未回连发企微通知）
- R2：A（`_switch_to(force=True)` 恢复路径绕冷却，前台切换仍受 300s 约束）｜B（冷却期允许连唯一候选）｜C（300→120s）
- **建议组合：A + A，可选叠加 R1 的 C。**

**报告**：`.workbuddy/artifacts/AP自动开启后不回连-20261003-根因分析与修复方案.md`

**附带观察（待确认）**：① 07:47:04 那次重启疑似"以为还坏着"，是 R1 造成的信息不对称；② 车机热点不稳是外部触发源；③ **建议把 `/var/log/teslausb-wifi.log`（v59 新增）补进 `routes/misc_routes.py` 的 `LOG_FILE_MAP`**，否则新日志对排障不可见。

**阻塞**：Tailscale SSH 校验过期（默认 12h），无法直连设备读 `/var/run/teslausb-ap-start-time`、`/tmp/ap-client-event.log`、`/var/log/teslausb-wifi.log` 三个文件复核"07:36:38 手动关闭 vs 事件回调让出"。已给一次性 re-auth URL。不影响 R1/R2 判定。
