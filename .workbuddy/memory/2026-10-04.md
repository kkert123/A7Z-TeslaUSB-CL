## 本轮：A7Z 蓝牙能力实测（为「AP 开启前加蓝牙验证」评估提供证据）

**问题**：用户设想把自动开 AP 加一道蓝牙验证——无法连 WiFi 时扫描是否有已知蓝牙设备，有则开 AP 并经蓝牙告知手机，无则不开。

**实测证据（`_logs/bt_probe*.py`，paramiko 直连设备）**：
- **A7Z 有蓝牙，且已可用**：`/sys/class/bluetooth/hci0` 存在，走 **USB**（`usb3/3-1/3-1:1.0`，驱动 `aic_btusb`；AIC8800 是 WiFi+BT 组合芯片）。`hciconfig hci0` = **UP RUNNING**，BD ADD `BC:2A:33:96:A5:D3`，名 `radxa-cubie-a7z`。
- **BlueZ 5.55 已装且运行**：`bluetooth.service` active（`bluetoothd` PID 452，开机至今）；用户态 `hciconfig/hcitool/bluetoothctl/btmgmt` 齐全（`bluetoothd` 在 `/usr/lib/bluetooth/`，不在 PATH）。
- **BLE 扫描实测可用**：`bluetoothctl scan on` / `btmgmt find` 均发现附近 LE 设备（如 `90:CE:B8:B0:DD:EE` rssi −55、`68:95:75:11:D0:ED` rssi −71）。控制器支持 LE + BR/EDR，**advertising 支持 16 实例**。
- 经典 `hcitool lescan` 在 AIC8800 上报 `Set scan parameters failed: Input/output error`（已废弃接口），须改用 `btmgmt`/`bluetoothctl`。
- 当前网络：`wlan0:connected:C12345`（家宽）+ tailscale 连接。

**评估要点（给用户的答复）**：① 手机 BLE 用 **RPA 可解析私有地址**，默认 ~15min 轮换，裸扫 MAC 不可靠（**除非先配对**——配对后 A7Z 存 IRK 可解析 RPA）；② 「经蓝牙推送到手机」需**配套 App**（iOS/Android 后台 BLE 限制严格），而项目已有**企业微信推送**通道可零 App 达成；③ 组合芯片 2.4G **共存**：AP 与 BT 扫描同时有干扰；④ 任何门控必须 **fail-open**（查不到也要开 AP，否则设备不可达比现在更糟）。已给 A/B/C 方案。

**未改动任何代码**——本轮仅硬件探测 + 方案讨论，待用户拍板方向。

## 本轮：WiFi 芯片并发能力实测（用户重提"AP/WiFi 同频共存"方案）

**用户新诉求**：① 能否让 AP 与 WiFi 用 2.4G 或 5G **共存**，从而不再来回切模式；② 若不行，改用**蓝牙**：连接 BT→开 AP、断开→关 AP，且仅限**白名单内已保存**的 BT 设备；③ 车机热点故障时保持"WiFi 重试"，除非检测到 BT 接入才切 AP。

**实测证据（`_logs/wifi_conc_probe*.py`）**：
- 芯片 = **AIC8800D80**（`usb 3-1: Product: AIC 8800D80`，`aicwf_usb_chipmatch USE AIC8800D80`）→ **双频**：`iw phy` 有 **Band 1（2412–2484 / ch1–14）** 与 **Band 2（5180+ / ch36+）**；驱动 `aic8800_fdrv` v6.4.3.0。
- **驱动声明支持 AP+STA 并发**：`iw phy` →
  `valid interface combinations: * #{ managed, mesh point } <= 1, #{ AP } <= 1, #{ P2P-client, P2P-GO } <= 1, #{ P2P-device } <= 1, total <= 4, #channels <= 3`
  → managed 与 AP 可**同时存在**（各 ≤1），最多 3 信道。`Supported interface modes`: managed/AP/AP-VLAN/monitor/mesh/P2P-\*；`HE Iftypes: Station AP`（WiFi6 双角色）。
- 即**旧结论"单射频不能共存"需修正**——那是当前**实现**（`hostapd.conf` `interface=wlan0`+`channel=6` 写死，AP 时 wlan0 `managed=no`+停 wpa_supplicant）的选择，不是硬限制。
- 工具：`iw` 在 `/sbin/iw`、`hostapd` 在 `/usr/sbin/`、`wpa_supplicant` 在 `/sbin/`——**均不在非登录 shell 的 PATH**（`command -v` 会误报 MISSING，须用绝对路径）。
- 当前 `wlan0`：managed、SSID `C12345`、**ch1 (2412MHz)**。

**结论/建议（给用户）**：① 并发若成立 → **紧急 AP 可常驻/按需，wlan0 始终作 STA**，从根上消除"切不回"；但须**同信道**（AP 跟随 STA），且需一次**带守护的实机验证**（远程只有 Tailscale 走 wlan0，直接试有自锁风险，未擅自执行）；② 蓝牙"连接→开AP"比"裸扫广播"强，但**触发端**仍是难点（手机不会主动连普通 BLE 外设，除非 App/HID/专用标签）；白名单可查 `bluetoothd` 的 bonded 列表（`/var/lib/bluetooth/<adapter>/<dev>/info`）；③ 任何判据须 fail-open + 手动出口。已给优先级：并发 > 蓝牙辅助。

**未改动任何代码**——仅硬件探测，待用户拍板。

## 本轮：AP+STA 并发「带守护网」实机验证（**成功**）

**用户**：「已经在车里了，先做带守护网的并发实机验证」。

**守护网设计**（关键）：设备端 `systemd-run --on-active=<N>` 瞬时定时器 → 到点无条件执行 `rollback.sh`（独立于 SSH 会话，SSH 断了也能自愈）；rollback = 杀测试 hostapd/dnsmasq → 删 iptables 测试规则 → 删非 wlan0 的全部 vif → `nmcli device connect wlan0`+`nmcli connection up C12345`（**不 restart NetworkManager**，M53）。先跑无害命令实证定时器机制 OK 再动。脚本上传后 `sed -i 's/\r$//'` 去 CRLF。

**测试脚本**：`_logs/apitest_run.sh`（v1 建 vif）、`apitest_run2.sh`（v2 防 NM 抢管+强制 AP）、`apitest_run3.sh`（v3 功能级 DHCP+NAT）、`apitest_rollback.sh`。

**结果（三层递进，全通过）**：
- **v1 发现**：`iw dev wlan0 interface add ap0 type __ap` → rc=0，**wlan0 STA 未受扰**（link 保持/ping 0%/tailscale 在线）；但 vif 被 udev 改名 `wlxb62a3396a9be` 且**类型仍是 managed** → hostapd 找不到 `ap0` 失败。根因：**NM 抢管新 vif 并锁成 managed**。
- **v2 修复并证实并发**：建 vif 后**立刻** `nmcli device set <if> managed no` + `iw dev <if> set type __ap` → `iw dev` 显示 **AP(ssid TeslaUSB-TEST, ch1) 与 managed(wlan0, C12345, ch1) 同时在线**，hostapd `AP-ENABLED`，wlan0 link 仍 C12345、ping 0%。
- **v3 功能级全通**：加 `ip addr add 192.168.42.1/24` + hostapd(ctrl_interface) + dnsmasq(`--conf-file=/dev/null --interface=<vif> --bind-interfaces --dhcp-range ...`) + `iptables -t nat -A POSTROUTING -s 192.168.42.0/24 -o wlan0 -j MASQUERADE`。实测：hostapd `state=ENABLED ch=1`；dnsmasq 监听 **192.168.42.1:53 + :67**；wlan0 仍连 C12345、ping 网关 0% 丢包。**AP 完整可用（广播+DHCP+DNS+NAT）且 STA 上行不掉**。
- **守护网验证**：手动触发 rollback → 设备干净恢复（仅 wlan0、连 C12345、IP 保留、Web 200）；定时器可正常停/清理。

**结论（方向性）**：**AIC8800D80 支持 AP+STA 并发已实机确认** → 用户"不再来回切模式"的诉求**技术上成立**。落地改动的关键点：① 新建 AP vif 而非复用 wlan0；② 建后立刻置 NM unmanaged + 强制 `type __ap`；③ AP **同信道**跟随 STA；④ 现有 `hostapd.conf`(`interface=wlan0`,`channel=6`) 与 iptables(`-i wlan0`) 规则须改为 AP vif 名。

**未改动仓库代码**（仅 /tmp 临时脚本 + 设备运行时态，已回滚）。待用户拍板是否立项改造。
