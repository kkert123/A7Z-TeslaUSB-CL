- **BLE 扫描实测可用**：`bluetoothctl scan on` / `btmgmt find` 均发现附近 LE 设备（如 `90:CE:B8:B0:DD:EE` rssi −55、`68:95:75:11:D0:ED` rssi −71）。控制器支持 LE + BR/EDR，**advertising 支持 16 实例**。

## 本轮：WiFi 芯片并发能力实测（用户重提"AP/WiFi 同频共存"方案）

**用户新诉求**：① 能否让 AP 与 WiFi 用 2.4G 或 5G **共存**，从而不再来回切模式；② 若不行，改用**蓝牙**：连接 BT→开 AP、断开→关 AP，且仅限**白名单内已保存**的 BT 设备；③ 车机热点故障时保持"WiFi 重试"，除非检测到 BT 接入才切 AP。

**实测证据（`_logs/wifi_conc_probe*.py`）**：
- 芯片 = **AIC8800D80**（`usb 3-1: Product: AIC 8800D80`，`aicwf_usb_chipmatch USE AIC8800D80`）→ **双频**：`iw phy` 有 **Band 1（2412–2484 / ch1–14）** 与 **Band 2（5180+ / ch36+）**；驱动 `aic8800_fdrv` v6.4.3.0。
- **驱动声明支持 AP+STA 并发**：`iw phy` →
  `valid interface combinations: * #{ managed, mesh point } <= 1, #{ AP } <= 1, #{ P2P-client, P2P-GO } <= 1, #{ P2P-device } <= 1, total <= 4, #channels <= 3`
  → managed 与 AP 可**同时存在**（各 ≤1），最多 3 信道。`Supported interface modes`: managed/AP/AP-VLAN/monitor/mesh/P2P-\*；`HE Iftypes: Station AP`（WiFi6 双角色）。
- 即**旧结论"单射频不能共存"需修正**——那是当前**实现**（`hostapd.conf` `interface=wlan0`+`channel=6` 写死，AP 时 wlan0 `managed=no`+停 wpa_supplicant）的选择，不是硬限制。
- 工具：`iw` 在 `/sbin/iw`、`hostapd` 在 `/usr/sbin/`、`wpa_supplicant` 在 `/sbin/`——**均不在非登录 shell 的 PATH**（`command -v` 会误报 MISSING，须用绝对路径）。
- 当前 `wlan0`：managed、SSID `C12345`、**ch1 (2412MHz)**。

**结论/建议（给用户）**：① 并发若成立 → **紧急 AP 可常驻/按需，wlan0 始终作 STA**，从根上消除"切不回"；但须**同信道**（AP 跟随 STA），且需一次**带守护的实机验证**（远程只有 Tailscale 走 wlan0，直接试有自锁风险，未擅自执行）；② 蓝牙"连接→开AP"比"裸扫广播"强，但**触发端**仍是难点（手机不会主动连普通 BLE 外设，除非 App/HID/专用标签）；白名单可查 `bluetoothd` 的 bonded 列表（`/var/lib/bluetooth/<adapter>/<dev>/info`）；③ 任何判据须 fail-open + 手动出口。已给优先级：并发 > 蓝牙辅助。

## 本轮：蓝牙「收发文件模式」配置（OBEX / Object Push）

**用户诉求**：把 A7Z 蓝牙配成可收发文件，用于手机↔A7Z 传音乐/文件。用户人在车里，现场测。

**关键发现/操作**：
- **A7Z 蓝牙原本缺 OBEX 组件**（`bluez` 只装了基础，无 `obexd`）→ 无 OPP/FTP 能力。
- **安装踩坑**：`apt-get install bluez-obexd` 报 404——**bullseye 安全池已 EOL**（`deb.debian.org/debian-security/pool/updates/main/b/bluez/` 只剩 bookworm 5.66 的包），但 apt 索引仍指向已删除的 `5.55-3.1+deb11u2`。**解法**：锁定 main 源版本装 `bluez-obexd=5.55-3.1+deb11u1`（main 池还有该 arm64 包）。`apt-get update` 不能解决（索引本身也指向坏版本）。
- 已装：`bluez-obexd 5.55-3.1+deb11u1` + `obexftp 0.24-6+b4`（+ 依赖 libopenobex2 等）。apt 顺带重启 `teslausb-fan/watchdog`——**确认仍 active**，未受影响。
- **obexd 运行方式（headless）**：Debian 提供的是 **systemd user service**（`/usr/lib/systemd/user/obex.service`，`BusName=org.bluez.obex`）。直接用 radxa 的 user bus 启动：`XDG_RUNTIME_DIR=/run/user/1000 systemctl --user enable --now obex.service`。加了 drop-in 覆盖指定接收目录+自动接受：`ExecStart=/usr/libexec/bluetooth/obexd -r /home/radxa/bt_received -a`。
- **验证成功**：obexd 启动后 `bluetoothctl show` 的 UUID 列表出现 **OBEX Object Push (1105)** + **OBEX File Transfer (1106)** + PBAP/MAP/IrMC Sync → **A7Z 成为 OBEX 文件接收端**。
- **可发现配置**：常驻 `bluetoothctl`（stdin 用 `sleep` 保持），注入 `agent NoInputNoOutput`（Just Works 配对）+ `system-alias TeslaUSB-A7Z` + `pairable on` + `discoverable-timeout 0` + `discoverable on`。结果：Alias `TeslaUSB-A7Z`、Powered/Discoverable/Pairable=yes、DiscoverableTimeout=0（永久可发现）。
- 接收目录 `/home/radxa/bt_received`（radxa 属主）。
- **paramiko 坑**：`nohup ... &` 后台进程若未完全脱离 stdout 会占住 SSH 通道 → `o.read()` 超时。须 `setsid`/完整重定向。

**给用户的建议（关键）**：① **iPhone 完全不支持 OBEX**（Apple 拒绝 OPP/FTP）——iOS 无法与 A7Z 蓝牙传文件，这是硬限制；② Android 可行但慢（~100KB/s–1MB/s），适合小文件；③ **更好的方案**：既然 AP+STA 并发已通，手机连 A7Z AP（手机仍有网）用网页/HTTP 传文件，速度快几十倍。

**测试态（未持久化）**：obex.service(user) enabled、`bluetoothctl` 常驻进程、适配器永久可发现——**均为测试临时态，需在测试后决定是否保留/回滚**。

**obexd 掉线修复（关键）**：`obex.service` 是 **systemd user 服务**，而默认 `Linger=no` → **SSH 会话一断，systemd 用户管理器退出，obexd 被一并杀掉**（日志实证 14:02:22 被 Stop）。修复：`loginctl enable-linger radxa` → 用户管理器常驻，obexd 跨会话存活（`obex.service` 用户态 `enabled` 只保证随用户管理器起，不保证用户管理器本身常存）。**凡 headless 场景下要长期运行的 user service，必须先 `enable-linger`。**

**配对卡住修复（关键）**：手机（**Samsung S20 FE**）点配对后卡住 → 手机显示「无法连接」。**根因**：配对走 **passkey/Numeric-Comparison** 确认，`bluetoothctl` agent 弹 `(yes/no)` 提示去**读 stdin**，而我的 `bluetoothctl` 是被 `sleep` 占着 stdin 的**哑进程** → 无人回 `yes` → `Request canceled`（日志实证 `[agent] Confirm passkey 256510 (yes/no): Request canceled`，两次）→ 配对失败。**做法**：`bluetoothctl` 的 stdin 改接 **FIFO**，写入者先发初始化命令、再**每 2s 喂一次 `yes`**（空闲时被当无效命令，无害；有确认提示时即被消费）。脚本 `/tmp/bt_agent_start.sh`（`setsid` 脱离）。

**✅ 实测成功（14:26）**：**手机(S20 FE) → A7Z 蓝牙传文件全链路打通**。配对成功（`bluetoothctl paired-devices` 显示 `Device 0C:8D:CA:77:DC:AB S20 FE`）；文件落到 `~/bt_received/Screenshot_20260630-103950_WeChat.jpg`（**714932 B**，有效 JPEG 1080×2400）——由 **obexd `-a` 自动接受**写入，无需人干预。

**反向 A7Z→手机：实测失败（硬限制）**：`obexftp -b <phone> -l`（FTP 浏览）与 `obexftp -U none -p`（OPP Push）**均失败**（`Connecting...failed: connect`）；BlueZ `obex Client1.CreateSession` 也 `Call failed`。根因：**Android 默认不运行任何 OBEX 服务端**（既不跑 FTP server，也默认不接收 OPP push）。结论：**蓝牙反向（A7Z→Android 手机）不可靠，不建议做**；反向应走 WiFi/HTTP（AP+STA 并发已通，手机连 AP 后网页上传/下载，双向都快）。

**测试态残留（需决定去留）**：① `bluez-obexd`/`obexftp` 已安装；② `loginctl enable-linger radxa`；③ obex user service enabled；④ `bluetoothctl` FIFO agent 常驻（`/tmp/bt_agent_start.sh` + `/tmp/btctl_fifo`）；⑤ 适配器永久 discoverable。**安全提示**：BT 永久可发现 + obexd `-a` 自动接受 = **附近任何人可向 A7Z 推送文件**；若做常驻功能，须加约束（仅已配对设备、限时可发现、大小/类型限制、隔离目录）。
