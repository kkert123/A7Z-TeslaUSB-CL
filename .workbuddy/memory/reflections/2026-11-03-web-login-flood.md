# 反思 - 2026-11-03（企微「Web登录成功」刷屏 / v0.3.1.67）

**日期**: 2026-11-03
**任务**: 定位并修复「企微机器人从下午起每约 30 秒推一条 Web 登录提醒」
**状态**: ⚠️ 结果成功（v0.3.1.67 已发布 + 真机验证刷屏停止），但**过程有明确偏差，被用户当场指出**

## 执行过程

- **用户第一句**：「读取下运行日志，微信机器人下午开始一直发送 web 登录信息……请查找问题所在，并按流程修复」。
- **我实际做的**：先在本地仓库 grep 文案（零命中）→ 去 D 盘找其它项目 → 探 Docker 主机端口 → **给出了一版错误结论**：「这条消息不是 A7Z 发的，是别的系统复用了同一个企微机器人 key」→ 让用户在两个错误选项里做选择。
- **用户纠偏**：「请直接从 A7Z 上调取日志」。三条命令之后，20 分钟内就锁定了 77 次重登 + 坏缓存文件。
- **最终**：根因、修复、测试、发布、真机验证全部闭环。

## 问题分析

- **表面原因**: 我在本机 grep 不到文案，就断定"功能不在这台设备上"。
- **根本原因**: **把「我找不到」当成了「它不存在」**，并且**优先级排序错了**——用户已经把现场指给我（"读取运行日志"），我却先去做架构推理（谁是发送方、哪台机器在 docker 里），把最便宜的取证（A7Z 免认证日志接口）放到了最后。
- **代价**: 约 20 分钟 + 一版错误结论 + 让用户在错误选项里选择（差点把排查引到 TeslaMate/其它系统上）。

## 具体错在哪（可复用的检查点）

1. **用户点名了设备，我却先去查"别的设备"**：正确顺序是「先在用户指的现场拿排除/确认证据」→ 再外扩。
2. **"不是这台"的断言门槛太低**：当时我手上的证据只有「本机 grep 不到文案」，而缺「设备上相关端点 404 + 进程/端口清单 + 全盘 grep + 日志零命中」这四项——其中三项我当时根本没做（`/login` 404 是后来才验的）。
3. **忽略了最便宜通道**：A7Z 的 `/api/logs/history`、`/api/logs/file-stream` **免认证**，一条 curl 就能读 journal；而我花时间去探 Docker 主机的 22/80/443/3000/3001/5000/8080 端口（全部不通，纯浪费）。
4. **把"通知里的字段"当成了事实**：`真实公网IP: 127.0.0.1` 其实是 `location_detector.login()` 硬编码进请求体的 `publicIp`。当时还据此推断"是别的系统在容器内探测公网 IP" —— 方向完全错。

## 做得好的

- 被纠正后**没有辩解**，立刻转向，且 3 条命令内收敛。
- 定位后没有停在"清掉坏文件让它不刷屏"，而是追到了**并发非原子写**这个根因，并做了原子写 + 损坏自愈。
- 自查阶段抓出两个会留坑的点：tmp 名用 pid 在同进程多线程会撞名；隔离坏文件可能误伤别的进程刚写好的新文件。
- 测试用真实事故形态（文件尾部多一个 `}`）做基线，而不是自己造一个"看起来坏"的文件。
