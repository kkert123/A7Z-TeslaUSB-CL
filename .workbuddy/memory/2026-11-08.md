### 被需求推翻的设计前提（值得记住）

方案 C 原本的卖点是「key 只存 B，A 不落地」。但用户要求「B 挂了由 A 发通知」——
B 挂了就不可能由 B 代发，所以 **A 必须持 key**。结论被迫改为「key 双持有」：
- A：`config/sentry.json` 的 `wecom_guard_webhook_key`（复用现成 bot 机制）
- B：`guard-b.env` 的 `GUARD_WECOM_KEY`

教训：**「谁能发消息」是由失效模式决定的，不是由安全偏好决定的**。设计安全边界时
先画失效矩阵，再决定密钥放哪，否则会在实现阶段被需求硬掰回来。

### 三处主动加强（都是写代码时发现的真问题）

1. **预热期 300s**：升级后 `web` 可能先于 `bgpreview` 起来 → `preview_scan.json` 不存在 →
   thumb 判 warn；bgpreview 首扫后变 pass → 推一条「注意 → 正常」纯噪音。
   一年升级十几次就是十几条假消息 → 预热期内只跟踪不推跃迁报告。
2. **待发报告用列表（≤3）而不是单槽**：单槽会让「B 侧失联」被随后一条自检报告覆盖。
   安全项不能丢（测试 G13 锁死）。
3. **`no_guard_bot_key` 不入重试队列**：配置问题重试一万次也不会成功，只 warning 一次。

### 顺手修掉的现存缺陷

- **`WECOM_BOTS` 前后端长期不一致**：后端 3 项（含 `boot`），前端 `templates/system.html`
  硬编码 2 项。前端那份**从未被使用**，却让人以为改那里就能加机器人 → 删掉。
- **`.status-dot` 在全项目没有 CSS 定义**：仪表盘模板里写的 `status-dot green` 一直是
  零尺寸空 span，用户根本看不见。已在 `static/style.css` 补样式。
- **`delivered: True` 无法区分 dry-run 与真发**：B 端 `alerts.py` 改三态 `sent|dryrun|failed`。

## 现场事故：一条 manual-test 心跳造成整夜假「设备失联」（M125）

用户早上收到「设备失联」但车停着、状态正常。根因不是判死逻辑，是**我给的联调 curl**
（`version=manual-test` + 我编的 `locked=true,sentry_mode=true`）被 B 端当真实心跳存进
`last_seen`/`last_body` → 判「该在线」→ 5min 后报失联 → `dedup_s=1800` 每 30min 重发；
而 A 端当时根本没配 `guard.json`，永远不会有"恢复"。

修（B v1.0.2）：`_is_test_body()` → `note_test()` 只记 `last_test`，不碰 last_seen/last_body；
文案 `_human_age()` + 「从未收到」+ 版本 + 建议；升级说明加清污染步骤。
