# 2026-11-03

## 企微「✅Web登录成功」刷屏 → v0.3.1.67（M114）

**现象**：企微「系统通知」机器人从下午起每约 30 秒推一条
「✅Web登录成功 / 内网/代理IP: 172.19.0.1 / 真实公网IP: 127.0.0.1 / 设备UA: python-requests/2.32.5」。

**排查路径（值得复用）**
1. 先在自己仓库与本机 grep 文案 → 零命中（A7Z 工作树确实没有该功能）。
2. 走 Web 日志 API（`/api/logs/history`、`/api/logs/file-stream`，**无认证**）读今日 journal，确认 A7Z 只有 `location_detector: TeslaMate 登录成功（token 已缓存）`，且 15:43–16:23 出现 **77 次**，约 31 秒一次。
3. 用户提供的新日志里出现 `保存 token 缓存失败: Extra data: line 8 column 1 (char 254)` → 直接去读 `/opt/teslausb-web/data/.teslamate_token.json`，**文件末尾多一个 `}`**（255 B），与报错字符位完全对上。
4. 设备 `requests` 版本实测 **2.32.5**，与通知 UA 一致 → 发送者就是 A7Z 自己（登录请求），推送方是 TeslaMate（docker，网桥 172.19.0.1）。
5. 通知里的 `真实公网IP: 127.0.0.1` 是 `location_detector.login()` 里**硬编码的 `publicIp` 字段**，不是公网探测结果。

**根因**：`.teslamate_token.json` 被 4 个进程共享（app / sentry_service / bg_preview_generator / notify-retry 一次性进程），旧写法是 `open('w') + json.dump` 非原子：两个进程同时从 offset 0 写，后写的短内容盖不掉先写的尾巴 → 尾部残留 `}` → 每次 `json.load` 抛 Extra data → 当成「无缓存」→ 每 31 秒重登 TeslaMate。

**修复（`location_detector.py`）**
- 写：`tempfile.mkstemp`（不能用 pid 拼名，同进程多线程会撞名）+ `os.replace` 原子替换，0600；附带 Windows 下 `os.replace` 撞并发读的短重试。
- 读：`JSONDecodeError` / 根节点非 dict → 隔离为 `.corrupt-<ts>` 后返回 `{}`；**隔离前二次校验**，避免误伤别的进程刚写好的新文件。
- 读取失败日志 debug → warning。

**验证**
- `_test_token_cache.py` 17/17（含 8 进程 × 60 轮并发写 + 高频读，读取端 0 次解析错误）。
- 回归 `_test_traffic_category` 30/30、`_test_service_refresh` 23/23、`_test_cleanup_guard` 36/36。
- 真机：坏缓存隔离为 `.corrupt-20261103-192700`；19:27:30 后重登 **0** 次、保存失败 **0** 次、位置检测仍正常（API 位置 4 次）；4 个常驻服务 cwd 全部 v67，`uptime -s` 未变（设备未复位）。

**发布**：commit `2efc9a5` → Release **432602660**，包 550095 B / SHA256 `ebe0ed03…`；三方核对全绿。回填 commit `7e563a2`。

## 复盘：排查顺序错了（用户当场纠正）

用户第一句就是「读取下运行日志」，我却先在本机 grep 文案 → 找别的项目 → 探 Docker 主机端口，绕约 20 分钟并给出**错误结论**（"不是 A7Z 发的，是别的系统复用 key"）。用户纠正「请直接从 A7Z 调日志」后，3 条命令就锁定了 77 次重登 + 坏缓存。
