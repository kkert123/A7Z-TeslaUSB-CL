# 登录鉴权设计说明 v2 —「仅验证码登录」

> 状态：**设计定稿待实施**。日期 2026-11-04。基线 v0.3.1.67。
> **本文件取代** `登录鉴权设计说明-已确认方案.md`（v1 的"密码 + 验证码"双因子模型已作废）。

---

## 0. 相对 v1 的变更

| 维度 | v1（已作废） | v2（本文件） |
|------|-------------|-------------|
| 凭据 | 密码 + 邮箱验证码（AND） | **仅邮箱验证码**（单一因子） |
| 发信前置 | 密码通过后才发码 | **challenge 票据校验通过 + 验证码生成成功后才发信**（D2） |
| 限流定位 | 第一道防线 | **第二道防线**（兜底，不承担"是否发信"的判定） |
| 离线兜底 | 本地网络 + 直接密码 | **待决策**（见 §10，无密码后这项没有天然答案） |
| 局域网段 | 启动自动采集 + 可改 | **用户手动填写**（D3） |
| SMTP | 任意 | **腾讯企业邮**（`smtp.exmail.qq.com`，D3） |
| 会话 | 允许多会话并存 | **登录成功即踢出其它所有会话**（D3） |

## 1. 决策基线

| # | 决策 | 边界 |
|---|------|------|
| D1 | 仅验证码登录，无密码、无定期改密 | 持有安全邮箱 = 可登录设备（**这是本方案的核心前提**） |
| D2 | 未生成有效验证码就不发信；限流只是第二道防线 | 发信前必须有可校验的"合法性证据"（challenge），不能是"点一下发一封" |
| D3 | 局域网段手填 / SMTP 用腾讯企业邮 / 登录后踢出其它会话 | 见 §7 §8 §6 |
| D4 | 单账号 `admin` | 审计靠 IP/UA 归因 |
| D5 | 首次启用仅本地网络 + 「发测试码→回填」闭环 | 未闭环不生效 |
| D6 | 安全邮箱禁止 tailnet 修改，只能走本地 Web 页面 | 三重校验：本地网络 + 已登录 + 同源表单 |

## 2. 整体流程

### 2.1 时序

```
① GET /login
   服务端签发 challenge（HMAC 签名票据：nonce + 签发时间 + IP/UA 指纹）
   → 渲染进页面（隐藏字段）；同时显示脱敏安全邮箱

② POST /api/auth/code/request   {challenge}
   ├─ 前置校验 1：challenge 签名有效、未过期（5 min）、未被使用
   ├─ 前置校验 2：challenge 绑定的 IP/UA 与本次请求一致
   ├─ 前置校验 3：该 challenge 下不存在"未过期的有效验证码"
   ├─ 生成 6 位验证码 → HMAC 存盘 → fsync 成功（生成失败则中止，不发信）
   ├─ 发送（腾讯企业邮）→ 收到 SMTP 250 才更新 last_mail_ok_at
   ├─ 第二道防线：限流（IP / 全局 / 每日）
   └─ 返回 {ok, sent_to:"cnl***@x.cn", cooldown:60, expires_in:300}

③ POST /api/auth/code/verify   {challenge, code}
   ├─ challenge 仍有效
   ├─ 恒定时间比较；失败 → 尝试次数+1（≥3 作废）+ 审计
   ├─ 成功 → 原子消费（一次性）→ session_epoch +1（踢掉其它会话）
   ├─ 新建会话（rotate session id）+ CSRF token
   └─ 跳转到"登录前意图"（见 §9.5）

④ 已登录访问 → 校验 session + epoch 是否等于当前值
```

### 2.2 发码请求的四道闸（顺序固定）

| 闸 | 判据 | 失败行为 |
|----|------|---------|
| 1 | challenge 签名 / 有效期 / 未使用 | 400 `4002`，**不发信**，不泄露原因细节 |
| 2 | challenge 与请求的 IP/UA 一致（弱绑定） | 400 `4002`；不一致记审计（可能是正常网络切换，故用"弱"绑定：UA 必须一致，IP 变化只记录不拒绝） |
| 3 | 该 challenge 无"未过期有效码" | **不发信**，直接返回 `{ok:true, reused:true}`（用户连点第二下不会再收一封） |
| 4 | 验证码已成功生成并落盘（fsync） | 500 `5001`，**绝不走 SMTP** |

> 四道闸全部通过才调用发信。限流（第五层）在发信前执行，但**它的作用是把风险压到可接受，而不是决定"这个请求是否合法"**——合法性由 1~4 判定。

### 2.3 为什么 challenge 不等于限流

- 限流是**统计性**的（"这个 IP 最近发太多了"），它拦不住"第一次就恶意"的请求。
- challenge 是**结构性**的（"这个请求是否真的来自一个由我们签发的登录页"），裸脚本必须先去 GET /login 拿票据，而票据与 IP/UA 绑定、5 分钟过期、一次有效。
- 两者叠加：challenge 保证"请求来自真实页面"，限流保证"即使来自真实页面也发不了太多"。

## 3. 职责边界（谁负责什么，不负责什么）

| 组件 | 负责 | **不负责** |
|------|------|-----------|
| 登录页（前端） | 展示脱敏邮箱、输入验证码、60s 倒计时、错误提示 | 不判断能否发信、不做限流、不决定降级 |
| challenge 服务 | 签发/校验票据，绑定 IP/UA，维护一次性 | 不生成验证码、不发信 |
| 发码服务 | 生成/存储/发送验证码，维护 `last_mail_ok_at` | 不校验验证码、不建会话 |
| 验证服务 | 校验并**原子消费**验证码 | 不重发、不建会话 |
| 会话服务 | 建会话、epoch 自增踢人、CSRF token | 不接触验证码 |
| 限流器 | 第二道防线（IP / 全局 / 每日） | 不决定"合法性" |
| 审计/告警 | 记录、去重、断网队列补发 | **不阻塞主流程**（异步） |
| SMTP 模块 | 只负责"把邮件交给腾讯企业邮并拿到 250" | 不生成验证码、不做业务判断 |

> 这条边界的作用：任何一层出问题都能单独替换（例如以后换 SMTP 服务商只动 SMTP 模块，不碰 challenge/验证逻辑）。

## 4. 关键校验点清单

| # | 校验点 | 位置 | 失败返回 |
|---|--------|------|---------|
| C1 | 静态资源放行 | 全局中间件 | — |
| C2 | session 有效且 `epoch == 当前值` | 全局中间件 | 页面 302 `/login`；API 401 `4001` |
| C3 | CSRF token 匹配（写方法） | 全局中间件 | 403 `4010` |
| C4 | challenge 签名/过期/已用 | 发码 & 验证 | 400 `4002` |
| C5 | challenge 与 UA 一致 | 发码 & 验证 | 400 `4002` |
| C6 | 无未过期有效码（发码时） | 发码 | 200 `reused`（不发信） |
| C7 | 验证码生成并落盘成功 | 发码 | 500 `5001`（不发信） |
| C8 | 限流未触发 | 发码 | 429 `4004` |
| C9 | SMTP 返回 250 | 发码 | 502 `4006`（提示"验证码发送失败，请稍后重试"） |
| C10 | 验证码匹配（恒定时间） | 验证 | 401 `4003` |
| C11 | 未超尝试次数（≤3） | 验证 | 401 `4003`（码作废） |
| C12 | 来源属本地网络（首次启用/改邮箱） | 安全配置 | 403 `4007` |
| C13 | reauth 在 5 分钟内 | 安全配置 | 403 `4008` |
| C14 | 同源 Referer + 表单来源 | 改安全邮箱 | 403 `4011` |
| C15 | 局域网配置格式合法 | 保存设置 | 400 `4012` |

## 5. 会话模型与「踢出其它会话」

### 5.1 用 epoch，不用会话列表

- 配置里维护 `session_epoch`（整数，落盘）。
- 登录成功：`session_epoch += 1`，新会话写入 `{sid, epoch}`。
- 中间件校验 `session.epoch == 当前 session_epoch`，不等即失效（302/401）。
- 效果：**新登录一次性让所有旧会话失效**，无需遍历/存储会话列表，重启后依然成立。

### 5.2 行为细节

| 场景 | 行为 |
|------|------|
| 同一浏览器多标签页 | 共享 Cookie，属**同一会话**，不互踢 |
| 手机 + PC 同时登录 | 后登录者生效，先登录者下次请求被踢到 `/login` |
| 升级/重启 | epoch 落盘，会话保留（`secret_key` 也落盘，见 §11） |
| 主动注销 | 只清当前会话，**不**改变 epoch（不影响其它设备） |
| 踢出后的提示 | 登录页显示"已在其它设备登录，当前会话已失效"（通过 `?reason=kicked` 传递，需白名单校验） |

## 6. 腾讯企业邮配置

### 6.1 参数（官方口径）

| 项 | 值 |
|----|-----|
| SMTP 服务器 | `smtp.exmail.qq.com` |
| 端口/加密 | **465 + SSL**（首选）；587 + STARTTLS（备用）；**25 不建议**（运营商常封） |
| 账号 | **完整邮箱地址**（如 `bot@yourdomain.com`） |
| 密码 | 企业邮箱密码；**若开启安全登录，必须用「客户端专用密码」**（16 位，只显示一次） |

### 6.2 前置条件（最常见的失败原因，必须写进设置页引导）

1. **管理员侧**：企业微信管理端 →【协作 → 邮件 → 安全管理 → 客户端访问权限】开启 `POP/SMTP` 或 `IMAP/SMTP` 服务范围。管理员没开，成员侧怎么配都不通。
2. **成员侧**：网页版企业邮箱 →【设置 → 收发信设置 → 开启服务】勾选 IMAP/SMTP（或 POP/SMTP）。
3. **安全登录**：若开启，需在【设置 → 邮箱绑定/账号安全 → 客户端专用密码】生成 16 位专用密码。

> 设置页的"测试发信"失败提示要能区分这三类原因，否则用户会反复怀疑端口填错。

### 6.3 三态校验（复用 `ups_stats.php` 那套思路，但更严）

保存 SMTP 配置前必须依次通过：
1. **格式校验**：host 域名合法、端口 1–65535、user 是合法邮箱地址、from 与 user 同域
2. **TCP 连通**：连接 `smtp.exmail.qq.com:465`（3s 超时）
3. **SMTP 登录 + 发信**：TLS 握手 → AUTH LOGIN → 发送一封测试邮件 → 返回 250

三步全过才允许保存；任一步失败给出**可区分的错误文案**（"连不上（网络/端口）" vs "认证失败（账号或专用密码）" vs "被拒信（额度/频率）"）。

### 6.4 发信额度

企业邮有日发信量限制与频率限制（因套餐而异，代码里不假设具体数值）。本方案的保护：
- 每日签发上限 **20 封**（远低于任何套餐限制，且够用：正常人一天登录几次）
- 单 IP 10 分钟 ≤5 次、全局 10 分钟 ≤10 次
- 收到 SMTP 拒信时**不重试**（避免越试越糟），直接提示用户

## 7. 局域网网段手动填写

### 7.1 字段

| 字段 | 类型 | 校验规则 |
|------|------|---------|
| `lan_cidrs` | string（逗号分隔） | 每个必须是合法 CIDR（`IPv4/prefix`，prefix 8–32）；最多 4 个；不允许 `0.0.0.0/0`；不允许包含 tailnet 段 `100.64.0.0/10` |

示例：`192.168.1.0/24, 192.168.42.0/24`

### 7.2 判定逻辑

```
未启用登录保护（首次配置阶段）：
  is_local_network := remote_addr ∈ 127.0.0.0/8
                    ∪ lan_cidrs（手填）
                    ∪ AP 段（192.168.42.0/24，内置常量，不可删）
                    ∪ 设备自身直连网段（自动探测，v0.3.1.70 / M118）

已启用：
  is_local_network := remote_addr ∈ 127.0.0.0/8
                    ∪ lan_cidrs（手填）
                    ∪ AP 段（192.168.42.0/24）
```

- AP 段内置不可删：设备自己开的热点，用户连上去配网时必须是"本地"。
- **首次配置必须并入「设备自身直连网段」（M118）**：`lan_cidrs` 正是要被配置的内容，它为空时若只认
  loopback + AP 段，用户在家里局域网（与设备 `wlan0` 同段）会被判"非本地" → `/api/security/*` 全 403 →
  网段永远填不进去，即 **引导死锁**。v0.3.1.69 真机实测：设备 `wlan0 12.127.12.115/24`，
  家里 PC `12.127.12.122`，被 `not_local_uninitialized` 连续拒绝 7 次。
  探测实现：`utils/auth_service.direct_iface_cidrs()` 解析 `ip -4 -o addr show`，
  **排除 `lo` / `tailscale*` / `docker*` / `br-*` / `veth*` / `virbr*` / `tun*` / `tap*` / `wg*`**——
  tailnet 不算本地（D6）这条不能被绕过。带 15 秒缓存；`ip` 不存在（Windows 开发机）时返回空列表。
- **已启用后回到严格口径**：只认手填网段，保留"用户可用 `lan_cidrs` 主动收窄"的能力。
- **启用前强制网段非空（M118）**：`POST /api/security/enable` 在 `lan_cidrs` 为空时返回 `4012`；
  同时 `GET /api/security/config` 返回 `suggested_cidrs`（探测到的直连网段），前端在网段框为空且未启用时自动预填。
  否则会有第二种自锁：在 AP 段或 loopback 上完成启用 → 回家才发现只有 AP 段算本地。
- **口径 C 的判据必须用严格口径**（`include_direct=False`）：未启用阶段直连网段临时算"本地"只是为了能进来配置，
  不代表"启用后还有权限"；用它算 `still_local` 会让二次确认被静默跳过。
- 保存时**不校验当前 IP 是否在新网段内**（否则改网段会把自己锁在外面），但保存成功后在页面顶部提示"当前 IP 不在新网段内，保存后将失去设置权限，请确认"。这是很关键的一个交互细节。

## 8. `?next=` 详解（你问的这条）

### 8.1 它是干什么的

**作用：登录后回到你原本想去的页面。**

你直接打开 `http://设备:5000/videos?folder=RecentClips`，但没登录 → 被跳到登录页。如果登录后统一跳首页，你还得重新点一次"RecentClips"。所以未登录跳转时会带上你原来的地址：

```
GET /videos?folder=RecentClips
  → 302 /login?next=%2Fvideos%3Ffolder%3DRecentClips
你登录成功
  → 302 到 /videos?folder=RecentClips     ← 就是 next 的值
```

`next` 的值应该是**站内路径**，服务端登录成功后跳过去。

### 8.2 开放重定向是怎么产生的

危险在于：**`next` 是用户可控的参数，而服务端如果无脑 `redirect(next)`，就等于让外部决定跳转目标。**

攻击链举例：

```
攻击者构造：  http://设备:5000/login?next=https://evil.com/fake-login
受害者收到：  "你的设备需要重新登录，点这里 → http://设备:5000/login?next=..."
受害者看到：  设备真实地址、真实证书/真实登录页 → 放心操作
受害者登录成功
服务端执行：  redirect("https://evil.com/fake-login")
受害者落到：  evil.com（页面做得和设备一模一样）
```

在**有密码**的方案里，这一步是钓鱼骗密码。在**你现在的仅验证码方案里，它更危险**：

> 攻击者可以做一个"假登录页"，提示"请先获取验证码"——用户点了之后，攻击者在自己那台设备上触发发码（如果他能连上），或者干脆直接骗用户"把刚收到的验证码填进来做身份确认"。**验证码一旦被填进攻击者的页面，攻击者立刻用它登录真实设备。**
>
> 这就是 OTP 钓鱼（real-time phishing）：**无密码方案没有"密码"可骗，验证码就成了唯一可骗的东西。**

常见绕过手法（如果你只用黑名单/contains 判断，都会被绕过）：

| 变体 | 说明 |
|------|------|
| `//evil.com` | 协议相对 URL，浏览器会当成 `http(s)://evil.com` |
| `/\evil.com` | 部分浏览器把 `\` 当 `/` |
| `https:evil.com` | 没有 `//`，但某些解析器仍识别为绝对 URL |
| `%2f%2fevil.com` | 编码后的 `//`，如果你先解码再判断顺序错了就中招 |
| `javascript:alert(1)` | 若前端用 `location.href = next` 会执行 |
| `/%0d%0aLocation:%20...` | 换行注入（HTTP 响应拆分，现代框架已挡，但仍要拒绝控制字符） |
| `http://设备:5000@evil.com` | `@` 前是"用户名"，真实主机是 evil.com |

### 8.3 正确校验（白名单式，不是黑名单）

**规则：只接受"站内绝对路径"，其余一律回落到 `/`。**

```
1. 取原始值，**只解码一次**（不要循环解码）
2. 拒绝：空、长度 > 512、含控制字符（\x00-\x1f）、含 '\\'
3. 必须以单个 '/' 开头，且第二个字符不能是 '/' 
4. 用 urlparse 解析：
   - scheme 必须为空
   - netloc 必须为空
   - 若解析出任何 host/port → 拒绝
5. 只保留 path + query（丢弃 fragment）
6. 校验失败 → 跳 '/'
```

判断顺序很重要：**先做"结构判断"（scheme/netloc 必须为空），再谈内容**。而不是"看它像不像外部域名"。

### 8.4 更推荐：干脆不用 URL 参数

最稳的做法是把"登录前的意图"存在**服务端会话**里，而不是在 URL 里传递：

```
未登录访问 /videos?folder=RecentClips
  → 服务端把 "/videos?folder=RecentClips" 写入匿名会话（或带签名的短期 cookie）
  → 跳 /login（URL 里只有 challenge，没有 next）
登录成功
  → 从服务端取出这个路径 → 校验（同 §8.3）→ 跳转 → 立即清除
```

好处：
- URL 里没有可篡改的跳转目标，攻击者**无法构造** `?next=` 钓鱼链接；
- 登录前意图是"服务端自己记的"，天然可信；
- 依然保留 §8.3 的校验作为第二层（防内部 bug）。

**建议：以 §8.4 为主，§8.3 作为兜底。** 二者叠加后，`?next=` 这个攻击面基本消失。

## 9. 离线场景（**必须你决策**）

### 9.1 问题

仅验证码方案有一个结构性缺口：

> **验证码由设备发送。设备没有外网 → 发不出验证码 → 你无法登录。**

而"设备出问题时"往往正是没网或网络异常的时候（车里无信号、AP 模式下无外网）。这和 v1 不同：v1 至少还有"本地密码"这条腿。

### 9.2 四个选项

| 选项 | 做法 | 优点 | 代价 |
|------|------|------|------|
| **L1 本地网络免验证码** | 来源在局域网/AP 段 → 直接登录 | 零记忆、零配置 | **局域网内任何设备都能登录**（蹭网即可控设备：能 reboot、能删录像、能格式化） |
| **L2 本地网络 + 本地密钥** | 离线时在本地网络输入一次性配置的"本地密钥"（10 位，非密码、不用定期改） | 安全性接近双因子；不依赖外网 | 需要保存一次（密码管理器/打印/贴设备） |
| **L3 离线不可登录** | 无外网一律拒绝 | 最安全 | 断网时完全无法配置设备（最需要的时候进不去） |
| **L4 离线只读** | 本地网络可看录像/日志，危险操作（reboot/format/改配置）仍需验证码 | 兼顾可用与安全 | 离线时改不了设置（含 WiFi） |

### 9.3 我的建议

**L2 + L4 叠加**：
- 离线 + 本地网络 → 输入本地密钥可完全登录；不输密钥则进入只读模式。
- 本地密钥在"首次启用"时生成并展示（与安全邮箱配置同一步），只显示一次。

理由：L1 的风险（蹭网者拿设备控制权 + 删哨兵录像）对一个"车载取证设备"来说太高——录像被删是不可逆损失。L2 只多了一次"保存密钥"的成本，而且**不是密码、不需要定期修改**，与 D1 的初衷不冲突。

如果你坚持零记忆，那就选 L1，但请接受"局域网内任何人可登录"这个前提，并且我会加上：每次 L1 登录强制告警 + 审计 + 顶部红色横幅。

## 10. 风险与边界

| ID | 风险 | 说明 | 缓解 |
|----|------|------|------|
| R1 | **邮箱被控 = 设备被控** | 仅验证码方案的全部安全性都押在邮箱上 | 安全邮箱开二次验证；与发送邮箱**不同账号**；登录告警；建议邮箱专用于设备 |
| R2 | **OTP 钓鱼** | 无密码可骗，验证码成为唯一目标（见 §8.2） | 不用 URL 传跳转目标（§8.4）；登录页固定文案；告警异常登录 |
| R3 | SMTP 凭据可被 root 读取 | AES-GCM 加密 + 0600 只防非 root | 用「客户端专用密码」（可单独吊销），不用主密码 |
| R4 | 邮件不达/进垃圾箱 | 用户会以为设备坏了 | 闭环验证 + 区分错误类型 + 本地兜底（L2/L4） |
| R5 | 时钟不可信（实测开机 87 分钟才 NTP） | 影响验证码有效期判断 | **TTL 用单调时钟**（`time.monotonic()`），重启后回退 wall 并标记 |
| R6 | 限流被刷导致自锁 | 攻击者刷配额 | 本地网络优先级更高；每日上限仅影响"发码"，不影响 L2/L4 登录 |
| R7 | 单账号无法追责 | D4 决定 | 靠 IP/UA 归因 |
| R8 | 配置非原子写 | `save_config` 现状是 `json.dump` 直写（M114 同类） | **前置必修**：改 `mkstemp + os.replace` |
| R9 | 告警风暴 | M114 教训 | 统一 30 分钟冷却 + 断网队列 |

### 14.7 交叉审查发现（2026-11-05）—— **P0 回归，已在 v0.3.1.69 修复**

oracle 三次尝试均失败（本机只有 Playwright Chromium、无系统 Chrome，
`--engine browser` 报 `Chrome window closed before oracle finished`），
改为手工逐面审查（认证绕过 / CSRF / 限流 / 会话 / 跳转 / 重放 / 竞态），
结果抓到一个**比安全漏洞更严重的可用性回归**。

#### 缺陷：守卫把 CSRF 校验放在「是否启用」之前 → 升级即破坏

`utils/auth_guard.py` 的检测顺序是「1 CSRF → 2 公开路径 → 3 未启用则放行」。
而 `session["csrf"]` 只在三处产生：`GET /login`、登录成功、`GET /api/security/config`。
**现有 16 个页面既不继承登录页逻辑，也没有任何一处会先写 csrf。**

前端口径（实测）：

| 项 | 数量 |
|---|---|
| 前端写请求（`method:'POST'`） | **67 处** |
| 带 `X-CSRF-Token` 的 | **2 处**（仅本次新增的 login.html / system.html 安全分组） |

因此升级到 v0.3.1.68 后，**即使一次都不启用登录保护**，切换模式、清理、
云上传、重启、保存配置等 65 处写操作全部返回 `403 {"error_code":4010}`。

实测复现（本机 Flask test_client，`is_enabled()==False`）：

```
enabled = False
POST /api/mode/switch       -> 403 {"error_code":4010,"message":"CSRF 校验失败，请刷新重试"}
POST /api/cleanup/execute   -> 403 {"error_code":4010,"message":"CSRF 校验失败，请刷新重试"}
```

**为什么真机影子验证 35/35 没抓到**：4.x 组测的是"鉴权链路能不能走通"
（登录页 → 发码 → 验证 → 踢人 → 只读 → 网段），从未测"**未启用时现有业务
接口是否还能用**"。这是验证设计的盲区，不是执行遗漏——新增横切关注点
（before_request 全局拦截）时，回归面必须包含"默认状态下旧功能不变"。

#### 两处修复（缺一不可）

| # | 位置 | 改法 | 解决 |
|---|---|---|---|
| F1 | `utils/auth_guard.py` | 把「未启用 → 放行」提到 CSRF 之前，**但 `/api/auth/` 前缀除外**（发码/验码是匿名入口，必须始终有 CSRF） | 升级后旧功能零变化 |
| F2 | `app.py` + `templates/base.html` + `static/app.js` | `context_processor` 向所有模板注入 `csrf`；base.html 输出 `window.__CSRF__`；app.js 装全局 fetch 拦截器自动加 `X-CSRF-Token` | **启用后**全站写操作可用 |

只做 F1 会让"启用后就全站失效"；只做 F2 会让"未登录访问仍 403"（拿不到 token）。
两项必须同版本落地。

#### 顺带发现的两处小问题（低危，同批清理）

1. `PUBLIC_PREFIX` 含整个 `/api/auth/`，使 `reauth` / `logout` 免登录可达。
   二者内部都做了 `check_session` / 清会话，**不构成绕过**，但应收窄为
   只公开 `status` / `code/request` / `code/verify` / `local` 四个。
2. `READONLY_ALLOW_POST = ("/api/auth/logout",)` 是死代码——第 2 步已整段放行
   `/api/auth/`，永远走不到第 5 步，删掉避免误导。

### 14.8 P0 回归修复与验证（v0.3.1.69，2026-11-05）

#### 最终守卫顺序（与 14.7 的初版方案有调整）

初版 F1 写的是「先 CSRF、再判启用」，但 G4 组测出问题：已启用 + 未登录时
返回 403/4010 而不是 401/4001——用户会话过期后看到「CSRF 校验失败」，
不知道要重新登录。**CSRF 攻击的本质是"借用受害者的已登录会话"，未登录时
没有权限可借**，所以改成三段式：

```
1 路径在 /api/auth/ 且是写方法        → 校验 CSRF   （匿名入口，不依赖会话）
2 公开路径                            → 放行
3 未启用登录保护                      → 放行（与上一版逐项等价）
4 会话无效                            → API 401/4001；页面 302 + 存原路径
5 已登录且是写方法                    → 校验 CSRF
6 只读模式                            → 写操作 403/4015
```

#### 实施范围

#### S1（待决策）：首次配置窗口的接管风险

未启用登录保护时，`/api/security/*` 的权限门是「仅本地网络，无会话也可操作」。
同一局域网内的终端可以：配自己的 SMTP → 用自己邮箱完成闭环 → `enable`
→ 主人被锁在门外（只能 SSH 恢复）。

**这是「未启用=无保护」这一已确认设计的直接后果，不是编码缺陷**，因此未擅自改。

缓解选项：
- **a. 安装令牌**（推荐）：首次启动生成一次性 token，打印到
  `/var/log/teslausb-web.log` 与串口；未启用时 `/api/security/*` 除本地网络外还需该 token。
- b. 缩短窗口：未启用超过 N 天自动拒绝远程配置（只留 loopback）。
- c. 接受：家庭 WiFi 本身有密码，视为可接受风险。

#### S2（未来隐患）：加反代后本地网络判定失效

若实施「方案 C（nginx 反代）」，Flask 退回 `127.0.0.1:5001`，则
`request.remote_addr` 恒为 `127.0.0.1` → `is_local_network()` 恒真 →
**「仅本地网络」的两道限制（离线登录、改安全邮箱）全部失效**。

到时必须同时改：
1. `_client_ip()` 改为「仅当 `remote_addr` 属于受信任反代 IP 时，才取
   `X-Forwarded-For` 的**最后一跳**」；
2. 反代侧 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for`；
3. 补测试：伪造 XFF 从 tailnet 发起，断言仍被判为非本地。
