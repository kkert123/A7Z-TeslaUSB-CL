# A7Z Web 访问认证方案评审（5000 端口）

> 状态：**设计评审，未实施**。日期 2026-11-03。前置事实来自真机实测（v0.3.1.67）。

## 0. 一句话结论

A7Z 的 Web 目前**没有任何认证**——不是"认证弱"，是**没有**。建议分两步：**先做方案 A（网络层收敛，当天可上）**，再上**方案 B（单口令 + 签名 Cookie）**作为正式认证；方案 C（nginx 反代鉴权）只在后续需要 HTTPS 或多设备证书体系时再引入。

---

## 1. 现状与风险

### 1.1 实测现状

| 项 | 实测值 |
|----|--------|
| 监听 | `0.0.0.0:5000`（`app.py` 直接监听，**前面没有 nginx/反代**） |
| 登录 | `GET /login` → **404**、`GET /api/login` → **404**，首页无登录页 |
| 全局钩子 | 只有 `@app.after_request`（禁缓存 HTML），**没有 `before_request`** |
| `secret_key` | 项目代码中**从未设置**（`/data/.secret_key` 是历史遗留文件，无人读取） |
| 会话机制 | 无 |

### 1.2 匿名可调的敏感端点（全量实测）

| 类别 | 端点 | 后果 |
|------|------|------|
| 系统控制 | `POST /api/system/reboot`、`POST /api/system/shutdown` | 任意 tailnet 节点可重启/关机 |
| 格式化 | `POST /api/system/format-teslacam` | **可格式化哨兵录像分区** |
| 升级 | `POST /api/version/upgrade`、`/api/version/upgrade-upload`、`POST /api/version/rollback` | 可推任意包/回滚 |
| 日志读取 | `GET /api/logs/history`、`/api/logs/file-stream`、`/api/logs/download` | 泄露路径、SSID、TeslaMate 地址、设备行为 |
| 配置读写 | `GET/POST /api/system/push-config`、`/api/system/wecom-config`、`/api/system/usb-guard-config` | 可改企微 webhook（钓鱼/静默关告警） |
| 媒体 | `/api/media/*`、`/api/video/*` | 可下载行车记录 |

### 1.3 威胁模型（按现实可能性排序）

1. **tailnet 内横向移动**：本机 tailnet 已有 10+ 节点（含 Android/HarmonyOS 设备、离线旧节点、共享给家人的设备）。任一节点被控 → 直接拿到设备控制权。
2. **误操作**：浏览器书签/自动化脚本误调 `reboot`、`rollback`，无需恶意即可造成事故。
3. **公网暴露**（当前未发生，但与 `guardian-b` 裸 IP 计划叠加后风险上升）：一旦做端口转发或 Funnel，等于把上述能力挂到公网。
4. **CSRF**：`POST /api/system/reboot` 若不校验 Origin/Token，用户浏览器访问恶意页面即可被跨站触发（目前**无任何 CSRF 防护**）。

> 结论：**认证是 P0**，不是"有空再加"。

## 2. 设备侧硬约束（决定方案可行性的边界）

| 约束 | 值 | 影响 |
|------|-----|------|
| 内存 | 总 959MB，`MemAvailable` ~390MB | 不能引入重组件；nginx 可接受（RSS ~5-8MB），Redis/Keycloak 不可接受 |
| Python | 3.9.2（Debian 11） | 只能用标准库 + 现有依赖；`hashlib.pbkdf2_hmac` 可用，无需装 bcrypt |
| 已有依赖 | Flask（含 itsdangerous）、requests | **签名 Cookie 可零新增依赖实现** |
| 前端形态 | 原生 JS + 多页面，`fetch` 分散在各页 | 加认证需要统一 fetch 拦截，否则漏改页面会静默 401 |
| 调用方 | ① 手机/PC 浏览器 ② 运维脚本（curl 调升级接口）③ 本机 systemd oneshot | 认证必须给脚本与本机留通道 |
| 升级机制 | Web 一键升级会**重启 web 进程自身** | 认证不能把"登录态"存在进程内存里，否则升级后全部失效 |
| 回滚 | symlink 切版本，秒级 | 认证改动必须可一键回滚（配置开关） |

## 3. 三个方案

### 方案 A：网络层收敛（绑定 + IP 白名单）

**原理**：不做"用户认证"，而是把"谁能连上"限制到可信网段。

**实现要点**
- `app.py` 增加 `@app.before_request`：校验 `request.remote_addr` 是否落在白名单
  - `127.0.0.1`（本机 oneshot / 自检）
  - `100.64.0.0/10`（Tailscale CGNAT 段）——可再收紧为具体节点 IP 列表
  - `192.168.42.0/24`（自家 AP 段，仅配网时需要）
  - 可选：家庭局域网段（配置项）
- 白名单外一律 `403 {"code": 4003, "message": "forbidden"}`，**不做重定向**（避免脚本拿到 302 当成功）
- **不信任 `X-Forwarded-For`**（当前无反代，信任 header 等于自废）
- 可选加固：把 `app.run(host=...)` 改为只绑 Tailscale IP（但 AP 配网场景需要 192.168.42.1，故保留 `0.0.0.0` + 白名单更灵活）

**优点**
- 改动最小：约 40 行，1 个文件，零前端改动、零脚本改动
- 无凭据管理、无新依赖、无额外进程
- 立即消除"公网/陌生网段可达"的风险

**缺点**
- **不是认证**：同 tailnet 内任一节点（含未来新增、共享设备）依然完全可用
- 无法区分"谁做的操作"，无审计
- tailnet ACL 一旦放宽，等价于全开
- 对 CSRF 无效（同源策略层面）

**工作量**：0.5 天（含测试与文档）。**风险**：低。**回滚**：删掉白名单函数即可。

---

### 方案 B：单口令 + 签名 Cookie（Session）+ CSRF Token

**原理**：设备上一个口令（家庭共享），登录后发签名 Cookie；所有请求校验会话。

**实现要点**
- **口令存储**：`/data/teslausb-web.json` → `web_auth: {salt, pwd_hash, pbkdf2_iter, token_hash}`；算法 `hashlib.pbkdf2_hmac('sha256', pwd, salt, 200_000)`（标准库，无新依赖）
- **初始口令**：首次启用时生成 10 位随机口令，**通过现有企微通知推送一次**，同时写 `/var/log/teslausb-web-auth.log`；不允许空口令启动
- **会话**：`app.secret_key` 从 `/data/.secret_key` 读取（文件已存在，改为真正使用）；`session` 存 `{uid:"admin", exp:ts, csrf:...}`，`PERMANENT_SESSION_LIFETIME=7d`，Cookie 属性 `HttpOnly=True, SameSite=Lax, Secure=False`（无 HTTPS 时不能置 True，否则浏览器不保存）
- **中间件**：`before_request` 白名单放行 → 静态资源（`/static/*`、`/favicon.ico`）→ 登录页/登录接口 → 其余校验 session，失败返回 `401 {"code":4001}`（XHR）或 302 到 `/login`（页面请求，用 `Accept: text/html` 区分）
- **CSRF**：session 内存一个 `csrf` token；所有 `POST/PUT/DELETE` 校验 `X-CSRF-Token` 头（前端统一拦截器注入）；**只对写方法校验**，读接口不校验（避免 GET 也被拦）
- **脚本通道**：`Authorization: Bearer <api_token>`，`api_token` 为独立随机值（存同一配置），与口令解耦——**升级脚本用它，绕开 Cookie**
- **本机豁免**：`remote_addr == 127.0.0.1` 免认证（供本机 oneshot 与自检），但**仍记审计日志**
- **升级鸡生蛋**：`/api/version/upgrade-upload` 用 `Bearer` token；升级重启后 `secret_key` 不变（读磁盘），会话不失效
- **登录提醒**：可选——登录成功推送企微（带 IP/UA），但**必须做去重/冷却**，否则就是本次 M114 的翻版

**优点**
- 真正的认证：能区分"有没有登录"，能审计
- 零新增依赖（Flask 自带 itsdangerous + 标准库哈希）
- 内存开销可忽略；升级后会话不丢（secret_key 落盘）
- 可逐步加强：加失败次数限制、加 TOTP

**缺点**
- 前端要改：所有 `fetch` 需要统一封装（拦截 401 → 跳登录；写请求注入 CSRF 头）。当前前端 `fetch` 分散在多页，**需要先做一次请求封装收敛**，否则漏改页面会"看起来打不开"
- 单口令共享、无多用户/角色
- 无 HTTPS 时口令与 Cookie 在链路上可被同网段嗅探（tailnet 内为 WireGuard 加密，可接受；自家 AP 明文网段需注意）

**工作量**：1.5–2 天（后端 0.5 天 + 前端 fetch 收敛与联调 1 天 + 测试）。**风险**：中（漏改页面导致功能不可用）。**回滚**：配置 `web_auth.enabled=false` 即时关闭（代码里读开关）。

---

### 方案 C：反向代理鉴权（nginx + Basic Auth / mTLS）

**原理**：认证从 Flask 剥出来交给 nginx；Flask 退回 `127.0.0.1:5001`。

**实现要点**
- `apt install nginx apache2-utils`（内存 +5~8MB）
- nginx `listen 5000`，`proxy_pass http://127.0.0.1:5001`，`proxy_set_header X-Real-IP $remote_addr`
- **C1 Basic Auth**：`auth_basic` + `htpasswd`；口令 base64 明文过网，**无 HTTPS 时不安全**
- **C2 mTLS**：自签 CA + 客户端证书；与 `guardian-b` 的"自签 + pinning"策略同源，强度最高
- 顺带获得：HTTPS、限流（`limit_req`）、访问日志、gzip

**优点**
- **零 Python 改动**（除监听端口），不碰业务代码，不会漏改前端页面
- 认证/限流/审计集中在一层，运维心智简单
- mTLS 强度最高；HTTPS 顺带解决口令明文问题

**缺点**
- 多一个常驻组件：A7Z 内存本就紧张，且 nginx 配置错误会直接导致 Web 全挂（新增故障面）
- **C1 无 HTTPS 等于没加密**；配 HTTPS 要证书（自签则手机浏览器告警）
- **C2 客户端证书分发麻烦**：手机/平板导入自签客户端证书体验差，家庭多设备场景维护成本高
- 升级包需要新增"部署 nginx 配置"的步骤，回滚要同时处理 nginx
- 与现有"Web 一键升级（不依赖 SSH）"流程耦合更重

**工作量**：1 天（C1）/ 2–3 天（C2 含客户端证书分发与手机验证）。**风险**：中高（新组件）。**回滚**：停用 nginx + 恢复 Flask 端口。

## 4. 对比表

| 维度 | A 网络收敛 | B 口令 + Cookie | C nginx 反代 |
|------|-----------|----------------|--------------|
| 是否"真认证" | ❌（仅限制来源） | ✅ | ✅（C2 最强） |
| 能区分用户/审计 | ❌ | ✅（单用户，但可记 IP/UA） | ✅（C1 用户名 / C2 证书） |
| 防 CSRF | ❌ | ✅（Token） | ⚠️ 需另配 Origin 校验 |
| 前端改动 | 0 | **中**（fetch 需统一收敛） | 0 |
| 脚本兼容 | 天然兼容 | 需加 `Bearer` token | 需加 `-u` 或客户端证书 |

| 内存增量 | 0 | ~0 | +5~8MB |
| 新增故障面 | 极低 | 低 | **中高**（配置错误即全挂） |
| 支持 HTTPS | ❌ | ❌ | ✅ |
| 实施周期 | 0.5 天 | 1.5–2 天 | 1（C1）/ 2–3 天（C2） |
| 回滚难度 | 极低 | 低（配置开关） | 中 |

## 5. 推荐路径

**第一期（当天）— 方案 A**
先把"谁能连上"收紧，零风险，立刻消掉公网/陌生网段可达 + 误触发概率。同时把 `X-Forwarded-For` 的信任策略明确写进代码注释（当前不信任）。

**第二期（1–2 天）— 方案 B**
做真正的登录态 + CSRF。**前置动作**：先把前端 `fetch` 收敛成一个封装（`static/js/api.js`：统一注入 `X-CSRF-Token`、统一处理 401 跳转），否则会漏改页面。这一步即使不做认证也值得做（当前各页 fetch 重复且无统一错误处理）。

**暂不做 C**，除非出现以下任一需求：需要 HTTPS 对外、需要多设备证书、需要按客户端限流。若真要做，优先 **C2（mTLS）** 而非 C1，因为 C1 在无 HTTPS 时等于明文口令。

**A + B 叠加是最终形态**：A 挡住不该来的连接，B 判断"来的人有没有登录"，C 只在需要 TLS 时补位。

## 6. 若采纳方案 B 的关键设计细节（待实施时确认）

1. **口令初始化不能"空口令放行"**：无口令时生成随机口令并推送一次，而不是允许无密码登录（否则一次升级事故就变成永久裸奔）。
2. **`secret_key` 必须落盘**：`/data/.secret_key` 读不到就生成并 `chmod 600` 写入；**不能每次启动随机生成**，否则每次重启/升级所有会话失效（用户会以为"又坏了"）。
3. **401 与 302 要按请求类型区分**：`Accept: text/html` → 302 到 `/login`；否则 401 JSON。否则脚本会把 302 当成功（历史踩坑：升级接口 302 → 脚本误判）。
4. **静态资源必须放行**：登录页要用 `static/` 下的 css/js，否则登录页自己打不开。
5. **本机回环豁免要记审计**：`127.0.0.1` 放行但记录调用路径，防止"本机脚本"变成后门却无人知晓。
6. **登录提醒要去重**：如果要推送"登录成功"，必须按 (IP, UA) 做冷却（≥10 分钟），并**只在新设备/新 IP 时推**——否则就是 M114 的翻版（把"本该静默的成功"变成刷屏源）。
7. **失败次数限制**：同一 IP 连续 5 次失败 → 锁定 5 分钟（内存字典即可，设备单用户场景够用）。
8. **回滚开关**：`web_auth.enabled` 放在 `config/sentry.json` 或 `teslausb-web.json`，**改配置即可关闭认证**，不需要切版本。
9. **升级脚本必须同步更新**：`_releaseNN.py` / 运维脚本里的 `curl` 调用要改为带 `Authorization: Bearer`，否则下次发版会卡在 401（**发版前必须验证一次**）。
10. **不要在本期顺手改监听地址**：只做认证，不改端口/绑定，避免把两个变量混在一次变更里（回滚时无法归因）。

## 7. 待确认项（需用户决策）

1. 认证范围：只保护**写操作**（reboot/format/upgrade/配置）还是**全站**（含视频与日志）？
2. 是否需要**多用户/不同权限**（例如家人只能看视频，不能重启）？当前设计是单口令共享。
3. 是否有**外部脚本/第三方面板**在用这些接口（如 Home Assistant、Node-RED）？需要为它们单独发 API Token。
4. 是否需要 **HTTPS**？（决定要不要引入 C 方案或自签证书）
5. 初始口令通过什么渠道给你？（企微推送 / 设备日志 / 首次访问页面设置）
