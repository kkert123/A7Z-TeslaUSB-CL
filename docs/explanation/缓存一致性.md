# 缓存一致性

> 解释 Present 模式下「读到的视频货不对板」的成因，以及解法是怎么一步步演进到现在的。
> 排障入口在 [排障手册](../how-to/排障手册.md)。

---

## 问题的由来

Present 模式下，`/dev/nvme0n1p2` 被两方同时使用：

1. USB Gadget 把它作为可写 LUN 绑定给特斯拉，车机实时写入
2. 本机以**只读**方式挂载在 `/mnt/teslacam`，供 Web 播放、缩略图生成、SCP 读取

为什么要只读？因为车机通过 Gadget 写盘时，本机和车机各自维护一套缓存。如果本机也挂载成可写，两边同时写同一个 exFAT 分区，文件系统必坏。

代价是：车机写了新内容，本机挂载的 VFS dentry/inode 缓存（文件名 → 簇的映射）**不会自动失效**。车机回收 RecentClips 的文件名并重写内容后，本机读取仍然命中旧簇 —— 视频字节货不对板。

Edit 模式为什么没问题？因为 Edit 模式会拆除 Gadget 并对分区重新 rw 挂载（附带 fsck），缓存从磁盘重建。两种模式读的是同一块盘，差异纯粹来自「只读挂载的缓存是否过期」。

## 解法演进

### 第一代：周期性暴力刷新（已废弃）

每 30 秒无条件执行一次 `drop_caches=2`（系统级清空所有 dentry/inode 缓存）。

问题：实测每天 3332 次。每次回收后本地读要重新从磁盘落盘，全系统 IO 重走磁盘。8 月 28 日系统僵死事故的成因之一。

### 第二代：读取驱动 + listdir 指纹（v0.3.1.31 / v0.3.1.35）

核心思路：**读取时刻 = 刷新时刻**。所有 teslacam 读取入口在读取前调 `ensure_fresh()`，30 秒 TTL 节流。

检测车机有没有在写，用 listdir 指纹（文件数 + 最新文件名）。

> 为什么不用 stat 目录 mtime？实测 Present 模式下 `stat` 目录的 mtime 被 inode 缓存冻结，感知不到特斯拉写入。而 listdir 因为 dentry miss 会强制读盘，能实时感知新文件。这是一个典型的「必须在真机上验证」的坑（[M52](../reference/教训索引.md)）。

### 第三代：延迟刷新 A1（v0.3.1.39）

第二代有个副作用：车机写哨兵期间，每次读取都会触发 `drop_caches`，实测累计 338 次。959MB 内存下，回收后本地读重新落盘，和 USB gadget 的写路径撞车 → dwc3 ep1out 端点禁用 → 车机写请求排不进队列 → **车机报 UI_a112「USB 设备故障 - I/O 错误」**。

改法：检测到车机在写，只标记 dirty，不立即刷；等车机停止写入满 60 秒（`WRITE_STABLE_SEC`）才执行刷新。

### 第四代：双语义（v0.3.1.40）

v0.3.1.39 把前台用户读取也一并延迟了，带来回归：车机持续写时，VFS 缓存可以冻结十几小时不刷，表现为无缩略图 + 播放失败。

分流语义：

| 调用方 | 参数 | 行为 | 理由 |
|--------|------|------|------|
| 前台读取入口（`video_routes` 列表/播放/缩略图 7 处、`serve_thumbnail` 懒生成） | `background=False` | 检测到写入**立即**刷 | 恢复「读取时刻 = 刷新时刻」，用户看到的就是最新的 |
| 后台兜底（`_coherency_loop`） | `background=True` | 静止 ≥60s 才刷（A1 延迟） | 无人浏览时零周期 drop_caches，保护车机写路径 |

### 第五代：bg_preview 恢复前台 + 读取驱动补漏（v0.3.1.41，当前）

第四代把 `bg_preview` 缩略图生成也归入 `background=True`（延迟刷），叠加下面的概率性认知，
带来回归：**无人访问时后台不再自动生成缩略图**（9-3 实证升级重启后 2.5 小时零生成，
手动打开 `/videos` 页触发一次前台刷新才恢复）。

两条修正：
1. **`bg_preview` 缩略图生成撤销 `background=True`（恢复前台立即刷）**——后台确定性生成。
   事件写完 ≥2min（scan 活跃窗口）才处理，drop 落在车机写间隙，频率 = 每新事件一次
   （30s TTL 防抖）；车机高密度持续写时可达 30-60s/次（与 A1 前实证期量级相当，接受，
   48h 观察 UI_a112，若复发给该路径加独立宽节流即可）。
2. **`/recent-clips` + `/api/camera/recent-thumbnails` 前置前台 `ensure_fresh`**
   （`camera_routes._sync_recent_clips_cache`）——补「读取驱动」缺口：列表接口此前只列
   已生成 JPG、从不刷新，页面打开后新事件要等后台生成才出现；现在页面打开/轮询即解锁，
   冻结期最坏 ~120s（S3 兜底）内有界更新。

**概率性认知（M58）**：readdir 目录列举读的是目录 inode 的 page cache——内存空闲时
缓存驻留，readdir 返回**冻结的旧文件列表**（感知不到车机新写）；只有内存紧张、page 被
挤出时才重新读盘。单文件路径 `open()` 的 dentry miss 才强制读盘。因此「后台任务靠
listdir 感知新事件」是不可靠的（依赖内存压力），需要前台 drop 解锁或接受概率。

## 当前机制一览

```
前台读取（video_routes + recent-clips 列表 + serve_thumbnail）──► ensure_fresh(background=False)
      ──► 检测到写入？──► 立即 drop_caches
      │否
      ──► dirty 悬挂？──► 立即刷（前台，用户操作优先）
      │否
      ──► 距上次 >120s？──► S3 兜底刷

bg_preview 缩略图生成 ──► ensure_fresh()（前台语义，事件写完 ≥2min 才处理）

后台兜底循环（60s）──► ensure_fresh(background=True) ──► 写入？──► dirty ──► 静止 ≥60s？──► drop
                        │否（无写入）                        │否
                        ▼                                     ▼
                      S3 兜底 120s                          继续等
```

关键常量（都在 `utils/cache_coherency.py`）：

| 常量 | 值 | 含义 |
|------|-----|------|
| `ENSURE_TTL_SEC` | 30 | 刷新节流窗口，防止读取连发时抖动 |
| `WRITE_STABLE_SEC` | 60 | 判定车机停写的静止窗口 |
| `S3_FORCE_TTL_SEC` | 120 | 兜底：指纹感知不到变化时的最长不刷新窗口 |

**S3 兜底为什么存在**：listdir 指纹只能感知文件集合的变化。如果车机用 `O_TRUNC` 同名覆盖重写，文件名集合不变，指纹检测不到。所以超过 120 秒即使指纹没变也强制刷一次。

## 设计取舍

**问：为什么不能在车机写的时候也读到最新内容？**

能，但代价是必须频繁 `drop_caches`，而这正是诱发车机 I/O 错误的原因。两害相权：

- 车机写的时候 → 读旧缓存，避免读到半截文件，也避免打断车机
- 车机停手后 → 任意读取触发刷新，读到最新完整文件

**问：`nmcli wifi list` 这类旧缓存返回怎么办？**

轮询时可能先拿到切模式前的旧扫描缓存。旧 SSID 是真实存在过的网络，实际连接会验证，连不上就走兜底逻辑，最多多一次失败尝试，不影响最终结果。
