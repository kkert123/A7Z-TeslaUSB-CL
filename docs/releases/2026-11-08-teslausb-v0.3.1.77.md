### 关键设计取舍

- **自检仍不告警**，只推"报告"：跃迁（跨档）/ 恢复 / 每日 20:00 摘要；同档 30min 去重。
  与 B 端判死职责分离，避免两套告警互相打架。
- **预热期 300s**：升级/重启后前 5 分钟只跟踪不推。否则 `preview_scan.json` 尚未生成导致
  thumb 短暂 warn，bgpreview 首扫后又变 pass → 每次升级都多一条「注意 → 正常」的噪音。
- **待发报告用小列表（≤3）**：单槽会让「B 侧失联」被随后的自检报告覆盖，安全项不能丢。
- **401 与超时分开**：`ping_kind ∈ timeout/unreachable/auth/b_5xx/config`，
  文案分别是「B 侧失联」/「令牌不匹配」。混在一起会把排查方向指错。
- **A 端直连企微不复用 `weixin_notifier`**：后者的推送点全部绑定「系统通知」bot，
  混在一起看不出哪条是设备失联；而且 B 挂了必须由 A 自己发。

### 3.1 测试心跳不再污染在线判定（v1.0.2 追加，M125）

2026-11-08 早上收到一条「设备失联」，但车明明停着、状态正常。根因**不是**判死逻辑：

- 前一晚为验证链路，我给了一条 `curl`，body 里 `version=manual-test` +
  `vehicle.locked=true,sentry_mode=true`（**这是我编的**）。
- B 端 `on_heartbeat` 一视同仁地写 `last_seen` + `last_body` → 判「该在线」→
  5 分钟后必然发「设备失联」，并按 `dedup_s=1800` **每 30 分钟重发**。
- 而 A7Z 当时 `guard.json` 还没配（`enabled=false`），**从未发过真实心跳** →
  这条告警永远等不到"恢复"，于是整夜重复。

修法：
- `judge._is_test_body()`：`test:true` 或 `version` 以 `manual/test/curl/selftest` 开头 →
  走 `state.note_test()`，**只记 `last_test`，不碰 `last_seen` / `last_body` / 在线判定**；
  接口返回 `{"event":"test","ignored":true}`。
- 文案重写：`_human_age()` 把人话时长（秒→分钟/小时/天）、「从未收到」单独成句、
  附「最后心跳的版本」与一句可执行建议；不再出现 `1794124165s前`、`None` 这类内部值。
- 升级包说明里加了**清污染步骤**（`mv state.json state.json.bak-<ts>`）：旧状态不会自己消失。

新文案示例：

```
【A7Z 自检】设备失联
最后心跳：16.1 小时前（0.3.1.76）
· Tailscale：16.1 小时前
· HTTPS：未启用

可能原因：断电 / 系统崩溃 / 网络中断（云端无法区分）
建议：确认车还停着，再检查设备电源与网络指示灯
```

## 4. 复核中发现并修掉的缺陷

两路独立审查（正确性 / 发布边界）。**2 个阻塞项**：

1. **仪表盘读错层级** —— `/api/guard/status` 把 `sender` 放在 `snapshot` 里，
   而 JS 读 `d.sender`。后果：**僚机那一行永远是「等待首轮心跳」的灰色，B 挂了也不变红**，
   正好废掉本次需求 4 的核心显示。已把 `sender`/`stale` 提到响应顶层，JS 同时兼容两种形状。
2. **待发报告「重试耗尽」后永久失效** —— 清空队列时没复位尝试计数，
   于是队列一旦清空，之后新入队的报告**一次都不再尝试**就立刻被判「耗尽」。
   已改为**逐条带计数**，并按优先级分档：安全项（B 失联/恢复）永不丢弃、
   普通报告 3 档（30/120/600s）后丢弃。

其余已修（非阻塞但都是真问题）：

- `_scrub` 用「重新读一次配置」拿 key，配置刚改过就会拿到新 key、旧 key 原样留在错误串里；
  且先截断 60 字再脱敏 → key 被切两半。改为**先脱敏再截断**，并用调用方手里的那把 key。
- `_ping` 只走 TS，TS 断了而 HTTPS 还通时会**误报「B 侧失联」**。已与 `_send` 对齐做 failover。
- 保存配置时不校验 `ca_path`：配了 HTTPS 但 CA 缺失 → 保存成功、线程启动、每次发送都失败入队
  → B 端 5 分钟后判「设备失联」。已改为 **400 直接拒绝**。
- `atomic_write_json` 的返回值被忽略：写盘失败仍回「已保存」，重启后配置回退。
- 扫描心跳阈值 300s → **600s**：一批缩略图的 ffmpeg 可能阻塞扫描循环数分钟，300s 会在干活时报假 warn。
- 日报改用 `(cur-target) % 1440`：`target=00:05` 时原来的减法整天不触发。
- `apply_config` 停旧线程后未等待 → 可能出现**两个心跳线程并存**；已 `join(timeout=2)`。
- 前端配置值未转义（配置是文件，可能是任意字符串）→ 加 `escapeHtml`。
- B 端 `bool("false") == True` → 统一 `config.as_bool()`；`runtime.json` 的 `alert_dry_run` 同样处理。
- B 端测试桩 `send_text` 返回 `True`（旧 bool 语义）→ 改 `"sent"`，避免假绿。
- 公网反代给 `/guard/config` 加 `return 403`（能改写告警 key 的接口只走 TS）。
