## 一、为什么改

用户 16:44 左右锁车，到 17:15 既没收到「停车自检」，B 端也没有任何告警。
B 端那半的问题已在 guardian-b v1.1.3 修掉（M135：判死闸把「A 死前最后一帧」当永久现状）。

A 端这半是另一条独立缺口：

| 现状 | 后果 |
|---|---|
| `_push_report()` 默认 `critical=False`，重试档位 `30 / 120 / 600s` | 第 3 档失败即**丢弃**，总共只争取到约 13 分钟 |
| `_pending_reports` **只在内存** | 车一睡（车机 USB 断电）/ web 进程重启 → 队列直接消失 |

而这次现场恰好命中：A 15:36:57 在 43 km/h 上失去网络（车载 MIFI/热点掉线），
锁车发生在 16:44——**报告连生成的机会都没有**；即便生成了，13 分钟后也会被丢弃。

用户明确要求：**「车辆锁车后无论正常与否，都要推送信息」**。只要 A 最终能联网
（回家 / 热点恢复 / 下次上车开机），这条报告就必须送到，而且要让人一眼看出
「这是几小时前的事」。

## 二、改了什么

### 1. 锁车报告升为 critical（永不丢弃）

```python
# guard_client.py · _maybe_lock_report
self._push_report(self._fmt_locked(snap, restarted=pending), critical=True)
```

`critical=True` 走 `_CRIT_BACKOFF = (30, 60, 300, 900)`，900s 封顶后**一直重试**，
且裁剪时优先保留——与「B 侧失联」同级，不再被普通自检报告挤掉。

### 2. 补发队列落盘（原子写）

- 新文件 `data/guard_report_queue.json`（`REPORT_QUEUE_PATH`），
  `atomic_write_json`（mkstemp + fsync + `os.replace`，M114/M122 的口径）。
- 条目结构 `{text, critical, tries, at, wall}`：
  - `wall`（墙钟）落盘 → 补发正文里能写「本条生成于 11-09 16:44」；
  - `at`（单调钟）**不落盘**，读回来一律置 `None` → 重启后立刻允许补发一次。
    （踩过的坑：用 `0.0` 当哨兵，在 `time.monotonic()` 是「开机秒数」时会被判成
    「冷却中」而拖住补发——M134。）
- 写点：入队、重试计数、成功出队、丢弃出队——**四处都同步落盘**，
  保证「第几次」跨重启可续（M124 的计数器未复位是同一类问题）。
- 读侧容错：坏 JSON / 非 list → 当空处理；条目超过 7 天 → 丢弃（补一条一周前的
  报告只会让人困惑）；空队列直接删文件，不留空壳。

### 3. 补发正文带「补发」标记

```
【停车自检】车辆已锁车 · 正常
设备：v0.3.1.83 → 100.111.252.121
...
（补发：本条生成于 11-09 16:44，当时无网络；现已补发）
```

不标注的后果比不补发更糟：几小时后收到一条「停车自检」，用户会以为车刚被锁。

## 四、附带修复：僚机卡片升级成功后停在「切换中」

现象（2026-11-10 00:54 现场）：B 端升级成功后，A 页面「僚机（B 端）版本」红框
一直显示 `v1.1.2 · 正在切换` 与 `切换中…（idle）`，**必须整页刷新**才变成
`v1.1.3`；点卡片里的「刷新」按钮没用。

三层原因叠在一起：

| # | 位置 | 问题 |
|---|---|---|
| ① | `guardian-b/deploy/apply.py`（root helper） | 写 `journal.json` 用 `mkstemp` + `mode=0600`，属主是 **root**。而 journal 是给 **guardb** 读的 → `Journal._load` 打不开 → 静默返回 `{}` → `public_status` 报 `idle`。**每次升级成功都会这样**，A 端永远等不到 `healthy` |
| ② | `templates/system.html` · `startPeerPoll` | 只把 `healthy` / `rolled_back` / `failed` 当终态，`idle` 落进 `else` → 永远打印「切换中…（idle）」，且**再也不调 `loadPeer`** → 卡片停在切换前的旧快照 |
| ③ | `templates/system.html` · 刷新按钮 | `loadPeer(true)` 生效后，3 秒一次的轮询立刻把提示改回「切换中…（idle）」→ 用户看到的就是"点了没反应" |

修法：

- `apply.py`：`write_json(..., owner="guardb", mode=0o640)`，写 journal 后 `chown` 到 guardb
  （`pwd.getpwnam`，失败只记一行日志）。⚠️ 该文件属 `.tools/`（**不在升级包内**），需单独 install。
- `upgrade.py`：`Journal._load` 把 `PermissionError` 单独接住并 **warning**，
  不再把「读不到」伪装成「没有任务」。
- `system.html`：抽出纯函数 `peerPollKind(st)`（`done` / `failed` / `gone` / `running`），
  `idle`/`verified`/空 一律 `gone` → **停轮询 + 刷新卡片**（按版本号判「已到达目标」则报 🎉）；
  新增 `peerRefreshNow()`（先 `stopPeerPoll()` + `peerStopWatch()` 再拉），刷新按钮改用之；
  轮询收尾用 `loadPeer(true, true)`（`holdMsg`）保证收尾文案不被覆盖；
  修掉 `stText[st] || ('· ' + st)` 的 falsy 兜底（`idle` 的空串被兜成灰字「· idle」）。

验证：

- 新增 `_test_peer_poll.js`（node）：`peerPollKind` 全状态断言 + 3 条接线静态断言 → **24/24**。
- 页面脚本语法检查（`new Function` 编译 87 KB）通过；`_test_guard_peer.py` 29/29。
