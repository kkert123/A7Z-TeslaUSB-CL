## 1. 这个版本解决什么

在此之前，「僚机（B 端）」是只读的：A 端只能看它报的状态，想升级得登 VPS、传包、跑 `install.sh`。本次把它变成可管理，但**刻意不给 A 端"换掉见证者"的能力**。

| 能力 | 实现 |
|---|---|
| 版本页显示僚机版本 | 新增「🛰 僚机（B 端）版本」区块：版本号 / 在线状态 / 升级状态 / A 端包库 |
| 上传 B 包 | A 端**先验签**再入库（坏包不上传、不占带宽） |
| 预置（不生效） | 推包 → B 独立验签 → 落到 `releases/<ver>.staged` |
| 人工确认 | B 生成 6 位确认码（绑 `job + pkg_sha256`，600s 有效），A 端输入后才切换 |
| 结果跟踪 | 轮询 B 的 journal：`committed → healthy / rolled_back`，失败自动回滚 |

## 2. 安全设计（这是本版的重点，不要当"额外工作"）

### 2.1 授权与加密分离

- 传输仍走 Tailscale（WireGuard），不新开端口、不新加证书；
- **授权靠签名，不靠共享令牌**：升级包的 manifest 由**离线开发机**的 Ed25519 私钥签名，namespace 独立（`a7z-guard-pkg`，与 A 自身升级包的 `file` 隔离）；
- A 端**只有公钥**。A 被完全拿下，攻击者最多让 B 下载一个"真实发布过的包"，无法让它生效。

### 2.2 B 端本地锁死（这是"锁死"的实际含义）

| 机制 | 效果 |
|---|---|
| 进程以 `guardb` 用户运行 | 对自己要执行的代码**没有写权限** |
| `ProtectSystem=strict` + `ReadWritePaths=/opt/guard-b/data` | `/opt` 变只读，只有 `data/` 可写 |
| `CapabilityBoundingSet=`（空） | 无任何 capability |
| 独立 root oneshot `guardb-upgrade.service` | **唯一**能写代码目录的进程 |
| `guardb-upgrade.path` 监听请求文件 | `guardb` 只能**写一个文件**；跑什么由 root 侧 unit 决定。不用 sudo（与 `NoNewPrivileges` 互斥） |
| `guard-b.env` 改 `root:guardb 0440` | 能读 key（要发告警）但不能改 key（防把告警改指到别处） |

### 2.3 文件校验（验的是"清单"，不是"包"）

```
manifest.json（被签名）
  {version, from[], files:[{path,sha256,mode}], removes[]}
     ↓ 解包时逐条体检
  拒：非普通文件 / 符号链接 / 设备 / setuid / 绝对路径 / ..
  拒：清单之外的文件（不做"跳过"，整包拒绝）
  拒：子目录（B 端模块是单层，多一层就说明包结构变了）
  拒：非 .py（**包内不允许任何脚本**）
  拒：guard-b.env / state.json / runtime.json / upgrade.py / apply.py
     ↓ 逐文件 sha256 双向比对
  再落地 → apply.py **重新核一遍** → 才写 releases/
```

### 2.4 不允许降级 / 重放

`.trusted/floor`（root 0444）记录最低允许版本，只在升级成功后前进；配合 manifest 的 `from[]`（允许起跳的版本列表）。

## 3. 升级期间不会再收到假「B 侧失联」

B 一重启，A 的 ping 必然连续失败。新增**落盘**的 900 秒抑制窗口（`data/guard_upgrade_window.json`）：窗口内只累计计数、不推送；窗口结束仍未恢复才判失联。

> 代价明说：窗口内若设备真的掉线，告警会晚到最多 15 分钟。这是为了避免"每次升级都误报一次"导致告警被无视 —— 而后者更危险。

## 4. 已知边界（必须知道，不是待修项）

1. **A 端「签名有效」只指签名**：A 不逐文件核 hash（那是 B 的职责）。篡改载荷 A 可能放过，B 必然拒绝。UI 文案与本文都按这个口径写。
2. **确认码防远程自动化，不防本机提权**：`guardb` 用户能读到 `data/upgrade/secret`，拿到 shell 就能自己算码。本机那道墙是沙箱 + root helper 的重新验签与哈希复核。
3. **`GUARD_UPGRADE_CODE_VIA_API` 默认 0**：确认码只出现在僚机本地日志里 —— 这才是真正的带外确认。设成 `1` 后 A 端能自动取码，省事，但"拿到 A 的攻击者"也能全自动完成，等于把人工确认降级成"人看一眼"。
4. **回滚只切代码**，不还原 `data/`。升级前建议 `cp -a data data.bak-$(date +%s)`。

## 5. 审查修正（两轮独立审查，6 个阻塞项全部修完）

| 问题 | 后果 | 修法 |
|---|---|---|
| `apply.py` 只核 hash 不验签 | 「改文件 + 改清单」即可让未签名代码进 `releases/` —— 这层校验等于不存在 | `stage_package` 把 `manifest.json.sig` 一并暂存；`apply.py` 落地前**重新验签** |
| journal 里的路径被直接拼接 | guardb 可写 journal → 可诱导 root 写/删任意文件（`/etc/passwd`、`../app.py`） | `safe_target()` 形状+realpath 双校验；staged 路径由 `version+job` **推导**而非采信 |
| guardb 直接 `systemctl` 会被拒（改加 sudo 也不行：`NoNewPrivileges=yes` 让 sudo 提不了权） | 升级永远不动，journal 卡 committed，后续每次 prepare 都 409 | 改用 `guardb-upgrade.path` 监听 `data/upgrade/request`；journal 卡住时 status 里标 `stalled` |
| 多个提前 return 不写终态 | 同上，卡死 | 全部走 `fail()` 写 `state=failed` |
| `StartLimitBurst` 落在 `[Service]` | 该指令被 systemd 忽略 → 崩塌后"自动回滚"也起不来 | 移到 `[Unit]`；`restart` 前先 `reset-failed` |
| 确认码默认经 API 返回 | A 被拿下时攻击者可自动读码+确认，人工确认层是摆设 | 默认改 `0`（只看僚机日志） |

| 项 | 值 |
|---|---|
| 部署包 | `guardian-b-deploy-v1.1.0.tar.gz` / 67,722 B / sha256 `b0abee208ac646d4bf4e3257bb2b3bbeff5b367e378a875063d6eb862eda8c9b` |
| 升级包（给 A 上传） | `guardian-b-v1.1.0.tar.gz` / 18,784 B / sha256 `9c7ea8b308d5eab8565653ff52f74735e1c782c7b678bbada2cbb72802a41fc9` |
| 打包工具 | `guardian-b/tools/pack.py`（离线签名；**必须先删旧 `.sig`**，否则 ssh-keygen 会交互式问覆盖→脚本挂起） |

**部署要点**：v1.1.0 改了目录布局（`releases/` + `current` 链接）与运行用户，`install.sh` 会自动迁移，但必须**先 `systemctl stop guard-b`**。详见 `guardian-b/INSTALL-TS.md` §10。

**不需要 sudoers**：`guardb` 只需能写 `data/upgrade/request` 一个文件，`guardb-upgrade.path` 监听到变更后以 root 拉起 `guardb-upgrade.service`。
`install.sh` 会 `enable --now guardb-upgrade.path` 并清理历史遗留的 `/etc/sudoers.d/guardb-upgrade`。
若升级卡在「已提交」不动，先查 `systemctl status guardb-upgrade.path` 与 `journalctl -u guardb-upgrade`；A 端状态里会出现 `stalled`。
