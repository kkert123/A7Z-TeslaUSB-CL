## 一、为什么 v0.3.1.81 上线后仍收不到

用户 10:37:04 锁车（车机显示 🔒已锁定 + 🔴哨兵开启），但守护一直认为「未锁」，直到 12:27 也没推。

三个问题串成一条链：

### ① TeslaMate 的 `locked` 与实际相反

```
/msg 实时：locked='false'   sentry_mode='true'   state='online'   shift_state='P'   speed='0'
车机实际：🔒 已锁定          🔴 哨兵开启
```

哨兵模式**只在锁车后开启**，所以 `sentry_mode=true` + `locked=false` 自相矛盾，`locked` 是错的（TeslaMate 侧陈旧/漂移）。

而三层兜底只在 `locked is None` 时才启用——这个**「有值但错」**的 false 让 L2/L3 永远没机会纠正。

### ② 重启后的首拍把「车已锁」当成「这一把锁已报过」

```python
if not self._locked_primed:
    self._locked_primed = True
    self._lock_reported = (cur is True)   # ← 旧实现
    return False
```

时间线：10:37 锁车 → 10:48:41 升级后重启 → 10:49 首拍时车已锁 → `_lock_reported=True` → 那条锁车事件**永久吞掉**。

### ③ 同一份漂移的 false 被当成「真解锁」

`_maybe_going_offline()` 只看 `prev.locked=True → cur.locked=False`，且**没有冷却**。日志实录：

```
Nov 09 12:15:28 预期离线握手已送达 reason=unlocked window=900s
```

每漂移一次就给 B 开 900 秒静默窗口，**恰好把「车已锁、设备将断电」时刻的失联告警关掉**。

## 二、改了什么

### 车态交叉校验（`_vehicle_snapshot`）

- `sentry_mode=true` 且车辆**确定停着**（`state != driving`、`shift_state not in (D,R)`、`speed <= 3`）时，把 `locked` 归一为 `True`，标 `locked_note=sentry_conflict`
- **加「停着」前提**是必需的：行驶中字段可能不同步，强判已锁会让 `_lock_reported` 闩锁卡住，反而吞掉真锁车
- `speed` 容错：该接口返回的是**字符串** `"0"`，原实现只认 int/float → 速度闸形同虚设
- 矛盾时打限流 warning（30 分钟一条），便于取证

### 重启后补报（`_maybe_lock_report`）

用户明确要求「每次重启都补一条」：

- 首拍时车已锁 → **挂起**一条（不再判为「已报过」）
- 预热期（启动后 300 秒）只挂起不推送：这段时间 bgpreview 还没写扫描心跳，自检会短暂 warn，报出去是假警报
- 预热结束后第一拍补推，文案标「重启后补报」
- 挂起标记的作废路径：解锁、车辆在动（D/R 或 speed>3）、用户关掉「锁车后推送停车自检」
- 冷却初值改为 `None`（=从未报过）：`time.monotonic()` 是**开机秒数**，用 `0.0` 当哨兵会让「开机不足 600 秒」被误判成冷却中

### 握手防抖（`_maybe_going_offline`）

- `cur.sentry_mode is True` 时不判「解锁」（哨兵还开着不可能真解锁）
- 同类跃迁冷却 1800 秒，但 **`driving` 不冷却**——一天多次出车是正常事件，冷却会把第二趟的静默窗口吞掉
- 冷却时刻改到**送达成功**后记账：握手最容易失败的时刻正是「车刚启动、网络在重连」，失败不该占冷却
- 冷却命中打 info 日志，便于排查

## 三、双审查修掉的问题

| 级别 | 问题 |
|---|---|
| **P0** | `_offline_at.get(reason, 0.0)` 在 monotonic 下等于「开机秒数」，开机不足 1800 秒时首次握手被当「冷却中」→ 每次用车/刚重启的第一次握手被吞 |
| P1 | 冷却按 reason 一刀切，把 `driving` 这类真实可重复事件也冷却掉 |
| P1 | 冷却在发送前落账，失败也占用，重试期内同一跃迁永久丢失 |
| P1 | 归一化缺「停着」前提，行驶中强判已锁 → 闩锁卡住 → 反而漏推真锁车 |
| P1 | `speed` 是字符串却被丢弃，速度闸恒不生效 |
| P1 | 关掉「锁车后推送停车自检」时挂起标记泄漏，重开开关会补推旧事件 |
| P1 | 测试没覆盖 `_maybe_report` 的接线（`dry_run=True` 被删掉也全绿） |
| P2 | 冷启动 10 分钟内锁车时，补报被 `_lock_report_at=0.0` 误判冷却拖住 |
| P2 | 挂起期间挂 D 档不清标记，几小时后挂 P 档会突然报一条 |

| P2 | 测试 C1c 在无网络环境下平凡通过（没有控制组断言） |

## 五、已知限制

- 归一化依赖「哨兵只在锁车后开启」这一特斯拉语义。若用户手动在车内开哨兵（官方语义下不成立），会出现一条假的「已锁车」；代价可接受，且文案会标「据哨兵推断」
- `SentryClips` 只在真的发生过哨兵事件时才产生新文件，L3 兜底不能完全替代 TeslaMate
- 同一进程内 `apply_config` 重建 sender 会重置闩锁 → 会补推一条（视为一次重启，符合用户「每次重启都补一条」的选择）

## 六、验证

升级后在车上做一次「开出去 → 回来锁车」：

1. 出车时日志应出现 `预期离线握手已送达 reason=driving`
2. 锁车后 30~90 秒内企微收到 `【停车自检】车辆已锁车 · 正常`（若 TeslaMate 仍报 false，会显示 `（据哨兵推断）`）
3. 若升级后立刻重启过，会额外收到一条 `（重启后补报）`
4. `data/guard_status.json` 里 `vehicle.locked` 应为 `true` 而非 `false`
