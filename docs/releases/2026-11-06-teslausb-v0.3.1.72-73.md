## 二、变更内容

### 需求

原来登录之后没有任何注销机制：会话一直有效，直到重启设备或别处登录把它踢掉。

### 实现

| 位置 | 改动 |
|---|---|
| `utils/auth_service.py` | 会话载荷加 `last_act`；`check_session()` 做**滚动空闲超时**（每次请求续期，写回节流 30 秒）；新增 `session_idle_minutes()` / `session_idle_seconds()`（1~240 夹取，配置非法回退默认 5）；`public_config()` 暴露该值 |
| `routes/auth_routes.py` | 新增 `POST /api/security/session/save`（`_require_admin` 门禁），保存后把当前会话重新计时，返回最新 `config` 供页面即时刷新 |
| `utils/auth_guard.py` | 超时跳转带 `reason=idle` |
| `templates/login.html` | 「长时间未操作，会话已自动注销」提示 |
| `templates/base.html` | 导航栏新增「退出登录」按钮（原来只有 `/api/auth/logout` 接口、**没有入口**） |
| `templates/system.html` | 「安全与登录」新增「登录有效期」区块（输入框 + 保存 + 回显） |

### v73 的兼容修正

v72 在会话缺少 `last_act` 时回退到 `auth_at`（登录时间）→ **升级瞬间**会让"登录得早但一直在操作"的用户被误判为"长时间未操作"。
v73 改为：没有 `last_act` 的旧会话**从本次校验开始计时**，不做时间回溯。

### 3.3 升级过程中的一处事故（已闭环）

用户在我执行设备端安装时中断。实际状态是：`do_upgrade_from_tarball()` **已完成**（软链已切 v72、数据已迁移），
但命令行调用**没有触发 `_schedule_restart()`**（那是 HTTP 路由里单独的一步），
于是出现「软链指向 v72、web/sentry 仍跑 v71、usb-guard 已跑 v72」的**混合状态**。

处置：补齐 6 个服务重启 + 单独重启 watchdog（v66 起有 magic-close，安全），最终 7/7 一致；
清理 `/tmp` 临时包。**未回滚**，因为安装本身完整、且混合状态停留越久风险越大。

## 四、回滚方案

```bash
ssh radxa@100.116.18.42
cd /opt/radxa_data
sudo ln -sfn /opt/radxa_data/teslausb-v0.3.1.71 /opt/radxa_data/teslausb
sudo systemctl restart teslausb-web teslausb-sentry teslausb-bgpreview \
                    teslausb-usb-guard teslausb-kernel-log teslausb-fan teslausb-watchdog
```

v0.3.1.71 目录仍在，未删除；`data/` 不会被回滚影响（每版目录各有一份，回滚后读的是 v71 那份）。
