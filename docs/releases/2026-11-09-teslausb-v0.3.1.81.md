## 1. 这个版本解决什么

用户报：**车辆行驶到目的地、下车锁车后，没有收到自检信息。**

查下来是三件事叠加，每一件单独都能让功能失效。

### 1.1 根因

| # | 问题 | 性质 |
|---|---|---|
| ① | `_vehicle_snapshot()` 读 TeslaMate `/states`，而该端点返回的是**服务配置状态**（`auto_del`/`buttons`/`schedule`/`mqtt_relay`/`share_config` …20 键），车辆字段在 **`/msg` 的 `raw_data`**（扁平 95 键，无 `vehicle_state` 层）→ `locked`/`state`/`user_present` **恒为 null** | **bug**（命名陷阱） |
| ② | 代码里没有「锁车」触发点，只有档位跃迁（`report_transition`）与每日 20:00 摘要 | **缺功能** |
| ③ | 兜底按「平铺」扫 `SentryClips`，而它是**事件子目录**（`SentryClips/<事件时间>/xxx-front.mp4`），顶层全是目录名 → 一个 mp4 都命中不了 | **bug**（实现时凭印象） |

①的连带影响被低估了：`_maybe_going_offline()`（出车/解锁自动握手）依赖 `vehicle.locked`，所以它**自 v0.3.1.76 起从未真正生效过**——之前每次升级要手工 `curl` 打 `going_offline`，根源就在这里。

## 2. 改了什么

### 2.1 数据源（`guard_client.py`）

- `_STATES_CACHE` → `_VEHICLE_CACHE`，`_states_refresh` → `_vehicle_refresh`，改调 `api.get_vehicle_data()`（`/msg` 的 `raw_data`）
- `_vehicle_snapshot()` 按**扁平**结构解析：`locked` / `sentry_mode` / `is_user_present` / `state` / `ui_park_time_str`，新增 `shift_state` / `speed`
- 新增 `detect` 字段标记锁车态来源：`teslamate`（权威）/ `clips`（推断）/ `sei`（推断）/ `none`
- 三态归一沿用 `_tri()`（`true`/`false`/`null`/字符串 `"nil"`）

### 2.2 三层兜底（TeslaMate 拿不到车态时）

| 层 | 数据源 | 判据 |
|---|---|---|
| L1 | `/msg` `raw_data` | `locked` / `shift_state` / `speed` |
| L2 | SEI（`utils/sei_parser`） | 最新**已写完**的 mp4 → `gear_state` + `speed_kmh` |
| L3 | 行车记录仪文件名 | **`SentryClips` 有新文件 ≈ 已锁车**（哨兵只在锁车后启动）；`RecentClips` 在写 ≈ 还在活动 |

L3 的判据来自 2026-06-01 的实测结论（SentryClips 永远没有 SEI，但只在锁车后录制）。两种目录布局都支持：`RecentClips` 平铺、`SentryClips`/`SavedClips` 事件子目录。

### 2.3 锁车必推（新功能）

- `_maybe_lock_report()`：`locked` 从 `False/None → True` 的边沿推一份**全量自检**，不看档位
- 三重防抖：**闩锁**（这一把锁报过就等真实解锁复位）、`lock_report_min_gap_s`（默认 600s）、300s 预热期
- 预热期用 `dry_run` 继续跟踪边沿——否则重启后 5 分钟内锁车的事件会永久丢失
- 命中锁车时**抑制同拍的档位跃迁报告**，避免「锁车 → gadget 判 warn」一炮双响
- 文案：`【停车自检】车辆已锁车（据行车记录仪）· 正常 / 分项 / 时间 · 版本`

### 2.4 配置（设置页守护分组）

- 勾选框「锁车后推送停车自检」（`report_on_lock`，默认 true）
- 数字项「锁车报告冷却」（`lock_report_min_gap_s`，默认 600，夹取 120~7200）
- `lock_detect_fallback`（默认 true，关掉就只用 TeslaMate）

## 3. 双审查

两路独立审查，**2 个 P0 + 6 个 P1**，全部处理：

| 级别 | 问题 | 修法 |
|---|---|---|
| P0 | `SentryClips`/`SavedClips` 是事件子目录，只扫顶层 → L3 的「已锁车」**永久不可达**，测试用扁平目录造数据给了假绿灯 | `_latest_clip` 增加子目录下钻（目录名即事件时间） |
| P0 | clips 推断出的 `locked=False` 会触发「解锁」握手（无冷却）→ 反复给 B 开 900s 静默，恰好关在「车已锁、将断电」窗口 | 握手只采信非兜底来源（`detect not in (clips, sei)`） |
| P1 | `True→None→True`（车休眠 `/msg` 返回 nil）会重新构成边沿，一晚上推 6 条 | 改为闩锁，真实解锁才复位 |
| P1 | `_sei_hint` 只正向缓存、失败不缓存 → 稳态每拍重读 26MB | 加负缓存（300s）+ 按 `name[:19]` 分组跳过最新**一组**（原来只跳一个摄像头文件） |
| P1 | 文件名时间来自车机 GPS，本机钟未同步时算成「未来」→ age 恒 0 | 负 age 视为不可信 |
| P1 | 改名残留 `_states_refresh_guarded` 引用已删除的名字（潜伏 `NameError`） | 删除 |
| P1 | 前端 `cfg.report_on_lock !== false`：字段缺失时显示「已勾选」 | 改 `=== true`（fail-closed，不假装已开） |
| P1 | 预热期整段跳过锁车判定 → 重启后 5 分钟内锁车永久丢失 | 预热期 `dry_run` 跟踪边沿 |

## 5. 遗留

| 项 | 说明 |
|---|---|
| L3 依赖哨兵事件 | `SentryClips` 只在**真的发生过哨兵事件**时才有新文件。「锁车但无事件」的场景 L3 判不出，只能靠 L1（TeslaMate）。因此 `report_on_lock` 的实际可靠性以 TeslaMate 可用为前提 |
| SEI 无自动化样本 | 仓库里没有可提交的 mp4 样本，L2 的解析路径只做了「失败降级」覆盖，未做「解析成功」覆盖 |
| `_SEI_CACHE` 命中键只有 path | 文件名被回收复用时可能命中旧结果（M64 同类风险） |

## 6. 文档修正

`docs/reference/TeslaMate接口与状态字段.md` 的 §2/§3 原本把 `/states` 写成「车辆实时状态（196 字段）」——**这就是本次错误实现的源头**。已改为「`/states` = 服务配置状态，`/msg` 的 `raw_data` = 车辆状态」，并补了 M133 警告块。
