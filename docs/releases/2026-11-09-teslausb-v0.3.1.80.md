## 1. 这个版本解决什么

用户实测：设置页「健康与通知 → 企业微信推送 → **A7Z 守护**」勾选「已启用」，勾选框**立刻弹回「已禁用」**，永远启用不了。连带自检四项里 `wechat` 长期 `warn`，整体显示「注意」。

### 1.1 根因：三段闭环，缺一不成

| 环节 | 代码 | 实际行为 |
|---|---|---|
| ① 勾选启用 | `templates/system.html::onWecomToggle` | `if (!input.value.trim()) { loadWecomConfig(); return; }` —— 输入框为空就重载列表，**一个请求都不发**，勾选被静默回滚 |
| ② 后端校验 | `routes/system_routes.py::api_system_wecom_config` | `effective_key` 为空直接 400。没 key 时切换必然失败（这个校验本身是对的） |
| ③ 填 key 保存 | `templates/system.html::saveWecomKey` | 取 `toggle.checked` 当 `enabled`，而它刚被①回滚成 `false` → key 被写进 `wecom_guard_webhook_key_disabled`，主字段仍为空 |

于是「配 key」和「开开关」互为前提：填 key 保存 → 存成禁用；勾选启用 → 静默回滚。第三圈回到起点。

### 1.2 为什么自检一起变黄

`guard_client._guard_bot_key()` 只读主字段（这是**正确**设计：key 被挪到 `_disabled` 就真的不发）。主字段空 → `_wechat_snapshot()` 里 `bot_key_set=False` → `_selfcheck()` 判 `wechat: warn` → 整体「注意」。配置好并成功推送一次后即转 `pass`。

## 2. 改了什么

### 2.1 前端（`templates/system.html`）

- **切换只发开关状态**：`onWecomToggle` 不再读输入框，直接 `POST {bot, enabled}`。后端在 `key` 为空时用 `cfg.get(base) or cfg.get(base+'_disabled')` 兜住，所以「有 key 但被禁用」能回到启用
- **三态渲染**：`已启用` / `已禁用`（有 key 但关掉）/ `未配置`。`未配置` 时勾选框 `disabled`，并在下方渲染**可见**橙色指引（`title` 在触屏/车机上不触发，等于没写）
- **失败可见**：切换失败时显示后端 `d.code === 'need_key'` 的专门文案，不再无声回滚；成功提示放到列表重建**之后**（先 show 会被 `innerHTML` 覆盖）
- **首次保存默认启用**：`firstTime = toggle.dataset.hasKey === '0'`（只认后端明确的「从没配过」；属性缺失时降级为「跟随勾选框」，避免把用户关掉的机器人悄悄打开）
- **轮询不再打断操作**：`loadWecomConfig(force)` 在非强制刷新时跳过三种情况 —— 焦点在 key 输入框、有未保存输入、有变更请求在飞（`wecomBusy`）。这条直接对应本次症状：30 秒轮询原本会清空正在粘贴的 key、并把刚切换的状态刷回旧值
- **永不 reject**：`el` 提到 `try` 外并判空，两处 catch 复用同一个引用。调用方用 `.then` 串提示，reject 会让提示静默丢失

### 2.2 后端（`routes/system_routes.py`）

- 无 key 时返回 `{'success': False, 'error': '请先填写 KEY', 'code': 'need_key'}`，让前端能区分「没配 key」与「其它失败」
- `new_key` / `current_key` 一律 `str(...).strip()`：历史手工值带空格时不再误报「KEY 格式无效」
- **格式校验只作用于新输入**：`if new_key and not re.fullmatch(...)`。沿用历史值时校验会把用户锁死 —— 既开不回来也关不掉
- `enabled` 严格布尔：`bool("false")` 是 `True`，外部脚本传字符串会被当成「启用」，与「禁用即真的不发」正好相反
- 原子写保持原文件权限：`mkstemp` 建的是 `0600`，`os.replace` 会把 `sentry.json` 从 `0644` 收窄，同机其它用户身份的进程读它会突然 `PermissionError`

## 3. 双审查

两个独立审查（前端交互 / 后端语义）结论均为**无 P0**，共 2 条 P1 + 若干 P2，处理情况：

| 级别 | 问题 | 处理 |
|---|---|---|
| P1 | 30 秒轮询无条件 `innerHTML` 重建，会清空正在粘贴的 key，且与切换请求竞态时能**复现原症状** | 已修（`force` 参数 + 三重跳过条件 + `wecomBusy`） |
| P1 | 唯一的操作指引写在 `title` 里，触屏永远看不到 | 已修（可见橙色提示行） |
| P2 | `catch` 里二次 `getElementById` 是唯一的 reject 源 | 已修（`el` 提前、判空） |
| P2 | `firstTime` 在属性缺失时降级为「强制启用」，方向危险 | 已修（只认 `'0'`） |
| P2 | 历史非法 key 既开不回来也关不掉 | 已修（正则只校验新值） |
| P2 | `mkstemp` 收窄文件权限 | 已修（沿用原 mode） |
| — 未做 | 并发读-改-写可能丢配置（需 `flock`）；自检把「用户主动禁用」仍判 warn | 记入待办，见 §5 |

## 5. 遗留（不阻塞本版）

| 项 | 说明 |
|---|---|
| 并发读-改-写 | 两个 bot 同时保存时，后写者用旧快照覆盖前写者 → 丢配置。需 `flock` 包住「重读→改→原子写」 |
| 自检的「主动禁用」语义 | 用户把守护机器人关掉后，`bot_key_set=False` 仍判 `warn`。应区分「配置缺失」（warn）与「用户主动禁用」（pass） |
| `push_bot_to_b` 只在启用时同步 | 禁用 guard 后 B 端仍持旧 key，继续发「设备失联」。属产品决策 |
