# 发布新版本

> 场景：改动已验证，要打成升级包发到 GitHub，让设备能检测到并升级。
> 整套流程有 5 个已知的坑，跳过任何一步都会发布失败或升级自举失败。

---

## 流程总览

```
改代码 → 审查 → 模拟运行 → 版本号 → 打包 → 完整性校验 → GitHub 同步 → 建 Release
```

---

## 第 1 步：版本号

`config.py` 的 `APP_VERSION` 是唯一版本来源：

```python
APP_VERSION = "0.3.1.40"
```

规则：`0.3.1.<递增>`。改完单独提交一次，commit message 用 `vX.Y.Z: bump APP_VERSION`。

```bash
git add config.py && git commit -m "v0.3.1.40: bump APP_VERSION"
```

---

## 第 2 步：检查未跟踪文件

**这是发布失败最常见的原因**（[M36](../reference/教训索引.md)）。新增的核心文件如果没 `git add`，它既不在仓库里、也不在升级包里，换机部署时直接缺失。

```bash
git ls-files --others --exclude-standard
```

输出里的每一个文件都要判断：该进仓库吗？该进白名单吗？

```bash
# 顺带确认没有漏提交的工作区改动
git status --short
```

---

## 第 3 步：打包

升级包由 `deploy_manager.py` 的 `MANAGED_FILES` 白名单驱动生成，产物是 `teslausb-v<version>.tar.gz`，落在本机 `.workbuddy/artifacts/`。

```bash
# 生成包后签名（私钥 upgrade_key 本地保管，不进仓库）
# 注意：upgrade_key 是 OpenSSH Ed25519 私钥，必须用 ssh-keygen -Y sign（SSHSIG 格式），
# 设备端 upgrade_service 的 _verify_ed25519 按此格式校验；openssl dgst 用不了这把钥匙
ssh-keygen -Y sign -f upgrade_key -n file teslausb-v<version>.tar.gz
```

## 第 4 步：完整性校验（M41 — 必做）

**白名单会漏文件。** 曾经漏了 18 个文件，设备升级后自举失败。唯一的可靠检查是跟历史完整包做 diff：

```bash
comm -23 <(tar tzf teslausb-v<上一版>.tar.gz | sort) \
         <(tar tzf teslausb-v<新版>.tar.gz | sort)
```

**输出必须为空。** 任何一行输出都是「上一版有、这一版没了」的文件，必须查清楚是故意删的还是白名单漏了。

同时确认包里包含 `requirements.txt` —— 缺了它，新 venv 装不出依赖，Web 起来就是 502（[M33](../reference/教训索引.md)）。

---

## 第 5 步：推送到 GitHub

git remote 已切 SSH（Deploy Key `~/.ssh/a7z_github`）：

```bash
git push origin main
```

推送失败时按这个顺序排查（[M48](../reference/教训索引.md)、[M49](../reference/教训索引.md)）：

| 现象 | 原因 | 处理 |
|------|------|------|
| SSL EOF / 连接超时 | 本机代理挂了（Clash 类 `HTTPS_PROXY=127.0.0.1:7890`） | `unset HTTP_PROXY HTTPS_PROXY` 后重试 |
| `github.com:443` 不通 | 端口被阻断 | 走 SSH 22 端口；或在 `~/.ssh/config` 配 `HostName 140.82.112.3` |
| `api.github.com` 正常但 git 不通 | 通道分叉 | Release 创建/资产上传走 API + PAT，git 走 SSH |

**先查代理再查别的。** GitHub API 全线 `SSL EOF(000)` 十有八九是代理的问题。

---

## 第 6 步：创建 Release

写一个 `_release<N>.py` 脚本，**从上一版成功脚本复制改造，不要凭记忆重建**（[M56](../reference/教训索引.md)）。

关键点：

```python
# 1) 幂等：tag 已存在先删除重建（body 修改会被缓存，M28）
st, out = api("GET", f"/releases/tags/{TAG}")
if st == 200:
    api("DELETE", f"/releases/{json.loads(out)['id']}")

# 2) 创建 release
api("POST", "/releases", {"tag_name": TAG, "name": TAG, "body": BODY})

# 3) 上传资产 —— ⚠️ 必须走 uploads.github.com
#    api.github.com/releases/{id}/assets 会返回 404（M56）
api("POST", f"/releases/{rel['id']}/assets?name={name}",
    binary=blob, host="uploads.github.com")
```

运行前 unset 代理：

```bash
unset HTTP_PROXY HTTPS_PROXY
python _release40.py
```

---

## 第 7 步：验证资产 SHA256

**发布后必须核对 body 里声明的 SHA256 与实际上传的资产一致**（[M26](../reference/教训索引.md)）。

```bash
sha256sum .workbuddy/artifacts/teslausb-v<version>.tar.gz
```

跟 Release 页面上的数字对比。不一致就 DELETE + 重建 Release（[M28](../reference/教训索引.md)）—— 直接改 body 可能被缓存。

新仓库如果没有任何 Release，`/releases/latest` 会返回 404，版本检查功能会一直报错（[M25](../reference/教训索引.md)）。要先建一个。

---

## 第 8 步：写 Release body

按 [发布说明规范](../reference/发布说明规范.md) 写。核心是：不讲内部流程，讲清楚「要不要升、升了变什么、要不要手动操作」。

发布前过一遍规范里的检查清单。

---

## 发布检查清单

- [ ] `config.py` 版本号已 bump
- [ ] `git ls-files --others` 检查过未跟踪文件
- [ ] `git status` 无遗漏改动
- [ ] `comm -23` 包 diff 输出为空（M41）
- [ ] 包内含 `requirements.txt`
- [ ] 推送前已 `unset HTTP_PROXY HTTPS_PROXY`
- [ ] 发布脚本从上一版复制改造
- [ ] 资产走 `uploads.github.com`（M56）
- [ ] 实际 SHA256 == body 声明的 SHA256
- [ ] Release body 过了[写作规范检查清单](../reference/发布说明规范.md)
- [ ] 设备上触发一次升级，确认升级后服务真的重启了（`systemctl is-active`）

---

## 升级后必做

设备端升级完成后：

```bash
systemctl is-active teslausb-web teslausb-sentry
journalctl -u teslausb-web -n 30 --no-pager
```

升级流程里必须**用 root 身份直接调 systemctl**，然后轮询 `is-active` 等待真正起来（[M43](../reference/教训索引.md)）。只发 restart 命令就返回，会留下「升级成功但服务没起」的假象。
