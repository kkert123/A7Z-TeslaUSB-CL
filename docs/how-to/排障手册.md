# 排障手册

> 按症状查。每条给出「先确认什么 → 怎么查 → 怎么处理」。
> 背景原理见 [说明](../explanation/架构总览.md)，很多问题是设计使然而非故障。

---

## 先做这三件事

不管什么症状，先收集这三条信息，能省一半时间：

```bash
# 1. 当前运行模式（present = 在车上，edit = 维护模式）
cat /tmp/teslausb_mode

# 2. 核心服务状态
systemctl is-active teslausb-web teslausb-sentry teslausb-gadget

# 3. 最近有没有刷屏的错误
journalctl -u teslausb-web -n 50 --no-pager | tail -30
```

**90% 的线上问题是最近一次部署引入的。** 先确认 `git log -3` 里改了什么。

## 车机报「USB 设备故障 - I/O 错误」(UI_a112)

### 先确认

```bash
# 看内核有没有端点禁用记录
dmesg -T | grep -iE "dwc3|ep1out|disabled endpoint" | tail -20

# 看缓存回收执行了多少次
grep -c "drop_caches" /var/log/teslausb*.log
```

### 成因

车机正在写数据时，A7Z 执行了系统级缓存回收（`drop_caches=2`）。959MB 内存下，回收后本地读要重新从 NVMe 落盘，和 USB gadget 的写路径撞车，dwc3 的出端点被禁用，车机的写请求排不进队列就报 I/O 错误。

### 处理

- **v0.3.1.39 之前**：升级。这个版本的修复是「车机写的时候只记标记，等它停手 60 秒再回收」
- **手动缓解**：`echo 2 | sudo tee /proc/sys/vm/drop_caches`（只应急，反复做会诱发问题）
- **判断修复是否生效**：车机写哨兵期间，日志里不应出现缓存回收

详见 [缓存一致性](../explanation/缓存一致性.md)。

## 车机认不出 U 盘

```bash
# 1. Gadget 是否激活 —— 空 = 未绑定
cat /sys/kernel/config/usb_gadget/tesla_usb/UDC

# 2. 分区是否挂载
mount | grep teslacam
ls /mnt/teslacam/TeslaCam/

# 3. 是不是 Edit 模式没切回来
cat /tmp/teslausb_mode
```

| 结果 | 处理 |
|------|------|
| UDC 为空 | `sudo systemctl restart teslausb-gadget` |
| 分区没挂 | `sudo /opt/radxa_data/teslausb/present_usb.sh` |
| 模式是 edit | 切回 present 模式 |
| 分区不是 exFAT | 重新格式化为 exFAT，并更新 fstab 的 UUID |

> 格式化后**必须更新 fstab 的 UUID**，否则下次启动进 emergency mode。

## 手机连 AP 配完网，A7Z 不切回 WiFi

### 先确认

```bash
journalctl -u teslausb-web --no-pager | grep "AP 自愈" | tail -20
```

日志里会打印 `已保存 N, 扫描到 M 个 SSID`：

- **扫描到 0 个** → 扫描没跑完就被判定了（v0.3.1.39 前的老问题）
- **扫描到若干个但 known 为空** → 确实没扫到已保存的网络，往下看

### 成因

AIC8800 从 AP 模式切回 station 模式，需要 10~30 秒才能扫到周围 WiFi。老代码只等 5 秒就去看结果，扫不到就误判「附近没网可连」，重启 AP 并把退避时间翻倍。

### 处理

```bash
# 看已保存的连接
nmcli connection show

# 手动触发一次重连
nmcli device connect wlan0
```

> 恢复网络时用 `nmcli device connect wlan0` 做**局部重连**，不要 `systemctl restart NetworkManager` —— 后者会打断 systemd-resolved 的 D-Bus 连接，导致本机 DNS 永久损坏（[M53](../reference/教训索引.md)）。

升级到 v0.3.1.39+ 后这个问题已修复（轮询等待扫描结果，最长 30 秒）。

## Web 打不开 / 502

```bash
systemctl status teslausb-web
tail -50 /var/log/teslausb.log
```

| 现象 | 原因 | 处理 |
|------|------|------|
| 502 | venv 依赖缺失 | 重装 `requirements.txt`（[M33](../reference/教训索引.md)） |
| 页面错乱/按钮无反应 | 前端 JS 异常 | `node --check static/app.js`，一个 ReferenceError 会让后续渲染全部停摆（[M22](../reference/教训索引.md)） |
| 改了代码没生效 | `.pyc` / 模板缓存 | 完整 stop → 清 `__pycache__` → start |
| 反复重启 | 服务崩溃循环 | 看日志里的 traceback |

## 缩略图不生成 / 播放失败 / 视频「货不对板」

这三个症状通常是同一个根因：**本机只读挂载的 VFS 缓存没失效**。

```bash
# 手动刷新一次缓存
echo 2 | sudo tee /proc/sys/vm/drop_caches

# 再看
ls -lt /mnt/teslacam/TeslaCam/RecentClips/ | head -5
```

刷新后内容正确 = 缓存问题。

| 具体症状 | 说明 |
|----------|------|
| 播放失败 | 读到的是写了一半的文件 |
| 货不对板 | 车机回收文件名重写，本机缓存还指向旧簇 |
| 无缩略图 | 缩略图生成时读到的文件不完整 |

**v0.3.1.39 的行为**：车机在写时故意读旧缓存（避免半截文件），停手 60 秒后才刷新。这是设计取舍不是 bug。

**v0.3.1.40 修正**：v0.3.1.39 把前台用户读取也一并延迟了，导致缓存长时间不刷新。40 版起前台读取立即刷新、后台兜底才延迟。

详见 [缓存一致性](../explanation/缓存一致性.md)。

## 系统卡死 / IO 风暴

```bash
# 看谁在刷 IO
iotop -o -b -n 3 2>/dev/null | head -30

# 看有没有子进程风暴
ps aux | wc -l
journalctl -u teslausb-web --since "10 min ago" | wc -l
```

典型成因：**子进程调用没做节流**。例如 `nvme smart-log` 每 5 秒调一次，10 分钟 197 次，直接把 Web 拖垮（[M34](../reference/教训索引.md)）。

处理：给这类调用加 TTL 缓存（建议 30 秒以上）。

## 升级失败 / 升级后服务没起

```bash
systemctl is-active teslausb-web
journalctl -u teslausb-web -n 50 --no-pager
```

| 现象 | 原因 |
|------|------|
| 升级包解压后脚本无执行权限 | Windows 打的 tar 丢执行位，需 `chmod +x *.sh`（[M35](../reference/教训索引.md)） |
| 502 | 包里缺 `requirements.txt` |
| 自举失败 | 包里漏文件（[M41](../reference/教训索引.md)） |
| 命令返回 0 但服务没起 | 用 root 直接调 systemctl 并轮询 `is-active`（[M43](../reference/教训索引.md)） |
| 页面一直显示"升级中"但版本没变 | URL 下载路径 stall 留下的 **stale `/var/run/upgrade_progress.json`** → 删掉它；下次改用 `upgrade-upload` 本地上传（[M92](../reference/教训索引.md)） |
| `readlink` 与 `APP_VERSION` 都是新的，**但行为还是旧的** | 见下一节（有旧代码进程没被重启） |

## 「版本号是对的，行为却没变」—— 先查有没有旧代码进程

**别只信版本号与 symlink。** 升级只重启 `web` 与 `usb-guard`/`kernel-log`；
其余常驻服务在 v0.3.1.66 之前**永远不会被升级重启**，会一直跑「已被删除的旧版本目录」里的代码，
旧行为以"看不见的写者/执行者"身份继续生效（[M106](../reference/教训索引.md)）。

```bash
# ✅ 唯一可信判据：逐个进程看它到底在跑哪份代码
for p in $(pgrep -f python3); do
  echo "PID $p -> $(readlink /proc/$p/cwd)  [$(tr '\0' ' ' < /proc/$p/cmdline | cut -c1-50)]"
done
# 出现 "…-v0.3.1.62 (deleted)" 这类即可疑
```

**多写者指纹：共享状态文件的数值"倒退"。** 单写者只会单调增。若 `data/traffic_stats.json`
（或任何被多进程共享的 json）出现某个计数变小，说明**有两个及以上进程各持一份内存快照、
轮流覆盖同一文件**——先数写入者，别急着怀疑业务逻辑。

```bash
# 观察同一文件在短时间内的两次取值
stat -c 'mtime=%y' /opt/radxa_data/data/traffic_stats.json; cat /opt/radxa_data/data/traffic_stats.json
sleep 25
stat -c 'mtime=%y' /opt/radxa_data/data/traffic_stats.json; cat /opt/radxa_data/data/traffic_stats.json
```

修法：`systemctl restart <那个陈旧服务>`，或依赖 v0.3.1.66 起的自动刷新
（`data/services_refreshed.json` 标记 + `startup_self_heal`）——详见 [服务清单 § 升级后服务刷新](../reference/服务清单.md)。

> 根因通常是「模块导入即 `thread.start()`」这类**导入副作用**：任何传递导入 `utils/app_helpers`
> 的进程都会悄悄起一个统计广播线程（`bg_preview_generator` 经 `cache_coherency` 懒加载就会）。
> v0.3.1.66 已改为入口显式 `start_broadcasters()`（[M31](../reference/教训索引.md) 同源）。

## 设备自己重启了 —— 先分辨「有序关机」还是「硬掉电」

```bash
uptime -p; uptime -s                     # 启动时刻
journalctl --list-boots | tail -5         # ⚠ 时钟回跳会让 journald 把多个 boot 合并成一条
journalctl -b -1 --no-pager -n 30         # 上一个 boot 的收尾：干净收尾 = 有序 shutdown

# 是不是"看门狗/usb_guard 主动要求复位"？（TTL 600s，消费后即删）
cat /opt/radxa_data/teslausb/data/usb_guard_reboot_request.json 2>/dev/null || echo "(无)"
grep -a "收到外部重启请求\|准备触发硬件重启\|已触发重启条件" /var/log/teslausb-watchdog.log | tail

# 有没有软件发起重启
journalctl --since "-1 day" --no-pager | grep -iE "COMMAND=.*reboot|systemctl reboot"
```

| 证据 | 结论 |
|------|------|
| 上一个 boot 的 journal **干净收尾**（`Stopped … / Reached target Shutdown`） | 有序关机（`reboot`/`poweroff`/外部断电前的正常停服） |
| 日志**戛然而止**、无关机记录 + 内核 `watchdog: … did not stop!` | 硬件看门狗复位（[M107](../reference/教训索引.md)） |
| 没有任何软件触发记录，且看门狗"守护进程启动"历史呈**不规则凌晨**分布 | 大概率**外部掉电/上电**（设备随车取电）——但日志被合并时**无法证实**，需如实标注为推断 |
| `uptime -s` 与 `systemctl show -p ActiveEnterTimestamp` **相差几十分钟** | 启动后时钟被校正（RTC 掉电不保时）；此时 `--list-boots` 不可信 |

**要变成可证**：每次启动把 `/proc/uptime`、`last reboot` 原始输出、本次启动原因写进
`data/boot_history.json`（不依赖 journald）。

## DNS 解析失败（`ping` 通但域名不通）

```bash
systemctl status systemd-resolved
resolvectl status
```

如果是执行过 `systemctl restart NetworkManager` 之后坏的：resolved 的 D-Bus 连接被打断导致崩溃，被 `Restart=always` + start-limit 限流卡住。

```bash
sudo systemctl reset-failed systemd-resolved
sudo systemctl restart systemd-resolved
```

**预防**：永远用 `nmcli device connect wlan0` 做局部重连，不要全局重启 NetworkManager（[M53](../reference/教训索引.md)）。

## 排不出来的问题

按「代码部署时间线 + 逐样本」双向验证，别只信「从什么时候开始出问题」的描述（[M42](../reference/教训索引.md)）：

```bash
# 时间线
git log --oneline -20
ls -lt --time-style=long-iso /opt/radxa_data/teslausb/*.py | head -10

# 逐样本：找一个具体失败对象，追它的完整链路
```

涉及内核缓存、挂载行为、udev 触发的逻辑，**必须真机验证**，纯代码审查抓不到（[M52](../reference/教训索引.md)）。
