# Bug 修复流程

> 场景：接到一个 Bug（用户报告、观察发现或真机验证失败），从定位到发布验证的完整处理流程。
> 三个阶段共 12 步。P0/P1 功能性 Bug 走全流程；文案、注释类改动可裁剪第 7-8 步审查。

---

## 流程总览

```
阶段一 · 定位与方案          阶段二 · 修复与审查          阶段三 · 发布与验证
1 Bug 信息结构化             5 修改代码                   9  构建校验
2 定位根因          ──→      6 语法检查          ──→      10 发布新版本
3 给出修复方案               7 easy-code-review           11 真机验证闭环
4 探讨并确认方案             8 AI 交叉审查                12 教训沉淀
        ▲
        └──── 验证未通过：带证据回到第 2 步重新定位（红色回环）
```

两条纪律贯穿全程：

- **证据不足不断言根因**——列出证据链和待排除项，不猜（[M42](../reference/教训索引.md)：排查按"代码部署时间线 + 逐样本"双向验证，别只信报告的时间分界）。
- **方案确认前不动代码**——第 4 步用户确认是硬闸门。

---

## 阶段一 · 定位与方案

### 第 1 步：Bug 信息结构化

接到 Bug 先补齐字段，缺什么问什么：

| 必备项 | 说明 |
|--------|------|
| 现象 | 用户能观察到的行为，不是猜测的原因 |
| 出现时间 | 精确到分钟，用于对时间线 |
| 设备版本 | `APP_VERSION` 或系统页显示版本 |
| 复现步骤 | 稳定复现 > 偶现 > 无法复现（无法复现要说明观测手段） |
| 日志/截图 | 相关日志片段、页面截图 |

信息不结构化，定位就是盲人摸象。

### 第 2 步：定位根因

- **先做版本关联分析**：问题版本前后改了哪些文件？是否触及相关模块？（参考 UI_a112 的定位路径：v0.3.1.31 引入 cache_coherency → v0.3.1.35 改指纹方式 → 时间线吻合）
- 双向验证：从代码部署时间线正推 + 从故障样本反推，两边对上才算实锤。
- 涉及内核缓存、挂载、USB gadget、systemd 生命周期的行为，**纯代码审查抓不到，必须真机实验**（M52/M53 的教训）。
- 输出：根因结论 + 证据链 + 已排除项。证据不足就明说"待验证"，不硬凑结论。

### 第 3 步：给出修复方案

每个候选方案都要写清三件事：

1. **具体改法**（改哪个文件、什么逻辑）
2. **影响范围**（哪些功能路径受影响）
3. **回滚方式**（出问题怎么退）

方案落地前过 **M59 三问**（v0.3.1.40 的学费——为护 UI_a112 把后台缩略图生成改死，2.5h 零生成）：

- 该路径是否核心功能的唯一保障？
- 有无双目标兼顾方案（只动兜底、不动主路径）？
- 无人值守场景下是否仍可达？

### 第 4 步：探讨并确认方案

把方案（含取舍）交给用户/团队确认。**确认前不改一行代码。**

---

## 阶段二 · 修复与审查

### 第 5 步：修改代码

- 最小改动，不顺手重构、不扩散范围。
- 改完先自查：拆函数后局部 import 作用域（M33/M34 类问题）、前后端字段名一致（M29）。

### 第 6 步：语法检查（按文件类型）

```bash
python -m py_compile <file.py>     # Python
node --check <file.js>             # JS —— 人工编辑粘贴损坏的重灾区（M30）
bash -n <file.sh>                  # Shell
```

全部通过才进审查。

### 第 7 步：easy-code-review

对照原始需求审查改动：是否只做了确认过的事、有没有夹带无关修改。

### 第 8 步：AI 交叉审查（分级处理）

审查发现的问题**分级**，不是全盘照收：

- **阻断项（P0/P1）**：必修，修完回到第 6 步重跑语法检查。
- **建议项（P2 及以下）**：先评估再决定，评估标准就是第 3 步的 M59 三问。接受的建议写明理由，拒绝的也写明理由。

---

## 阶段三 · 发布与验证

### 第 9 步：构建校验

发布流程细节见[《发布新版本》](发布新版本.md)，此处只列 Bug 修复发布必过的检查：

```bash
# M36：未跟踪文件检查（新增文件没进仓库 = 包里没有 = 换机缺失）
git ls-files --others --exclude-standard

# M41：与上一版完整包 diff，输出必须为空
comm -23 <(tar tzf teslausb-v旧版.tar.gz | sort) <(tar tzf teslausb-v新版.tar.gz | sort)
```

### 第 10 步：发布新版本

- `APP_VERSION` 递增 + 单独 bump commit。
- SHA256 计算并写入 Release body；资产上传走 `uploads.github.com`（M56）；GitHub API 失败先查本机代理（M49）。
- Release body 按[《发布说明规范》](../reference/发布说明规范.md)写（M57）：标题用用户能观察到的现象命名，禁 AI 腔。

### 第 11 步：真机验证闭环

**发布不是终点。** 升级后必须确认：

- 服务真正重启了（root 直连 `systemctl` + `is-active` 轮询，M43）；
- 原问题消失（用第 1 步的复现步骤回归）；
- 相关功能不受影响（按第 3 步声明的影响范围逐项验证）；
- 需要观察期的写明时限（如 UI_a112 的 48h ep1out 观察）。

### 第 12 步：教训沉淀

- 新踩的坑追加到 [教训索引](../reference/教训索引.md)：编号递增 + 版本号，**不要只写进本地 memory**（memory 不进仓库，知识传不下去）。
- 工作日志记录：根因、修法、验证结论、遗留观察项。

验证未通过 → 带上真机证据回到第 2 步重新定位，不原地打补丁。
