# 服务清单

> `services/` 下所有 systemd 单元。装机时全部复制到 `/etc/systemd/system/` 后 `daemon-reload`。

## 常驻服务

> 下表以 **设备实况** 为准（2026-10-15 逐单元核对 `LoadState / is-active / is-enabled`）。
> ⚠️ 仓库里仍留有一份 `services/teslausb-gadget.service`，但**设备上并不存在该单元**——gadget 生命周期的唯一 owner 是 `present_usb.sh`（由 `teslausb-mode.service` 调用，[M74](../reference/教训索引.md)）。不要照文件名臆测设备上有什么。

| 单元 | 用途 | 重启影响 |
|------|------|----------|
| `teslausb-web.service` | Flask Web 服务，监听 5000；**启动时会跑 `startup_self_heal()`，升级后由它触发其余服务的刷新**（[M106](../reference/教训索引.md)） | 短暂无法访问，不影响车机写入 |
| `teslausb-sentry.service` | 哨兵事件检测主进程 | 期间的事件会漏检 |
| `teslausb-bgpreview.service` | 后台缩略图预生成（**曾漏记**：它也是常驻服务，且会懒加载 `utils/app_helpers`） | 缩略图不再预生成，首次访问变慢 |
| `teslausb-usb-guard.service` | USB Gadget 链路守护（线在位+`state=='configured'` 判据，阶梯恢复/拔线闸/熔断；含 **Edit 模式闸**，见 [M80](../reference/教训索引.md)/[M82](../reference/教训索引.md)/[M103](../reference/教训索引.md)） | 触碰/插拔后的链路卡死不再自愈 |
| `teslausb-kernel-log.service` | 持久化内核日志采集（直读 `/dev/kmsg`，落盘 `data/kernel_live.log`，绕开 journald 盲区，见 [M83](../reference/教训索引.md)） | 失去内核级取证的持久落盘能力（故障复盘少一条证据源） |
| `teslausb-watchdog.service` | 硬件看门狗 | ⛔ **禁止用 `systemctl restart` 升级**：必然整机复位（[M107](../reference/教训索引.md)）。改代码只能靠整机重启生效 |
| `teslausb-fan.service` | 风扇控制 | 温度升高 |
| `teslausb-mode.service` | 开机决定 Present / Edit 模式（oneshot） | — |
| `teslausb-io-tune.service` | I/O 性能调优（oneshot） | 性能回落 |
| `teslausb-boot-notify.service` | 开机企业微信通知（oneshot） | 漏一次开机通知 |

### 升级后服务刷新（[M106](../reference/教训索引.md)）

`upgrade_service._refresh_project_services()`（注册在 `startup_self_heal()` 钩子链里）会在
**每次 `teslausb-web` 启动时**按版本号幂等地把 `sentry` / `bgpreview` / `fan` / `watchdog`
重启到当前版本（`usb-guard` / `kernel-log` 由各自的钩子负责；`web` 是它自己，不重启）。

- 幂等标记：`data/services_refreshed.json`（`{"version": "...", "refreshed": [...]}`），跨升级存活
- 只重启 `is-active` 的服务（尊重手动停用）；失败**不写标记**，下次启动重试
- **判据**：`for p in $(pgrep -f python3); do readlink /proc/$p/cwd; done` ——
  **不要**只看 `readlink /opt/radxa_data/teslausb` 或 `APP_VERSION`，那会被"未重启的旧进程"骗过

在有这个机制之前，升级只重启 web 与 usb-guard，其余服务会一直跑**已删除的旧版本目录**里的代码，
旧行为以"看不见的写者"身份继续生效（10-15 实证：统计文件被两个进程轮流覆盖，数值出现倒退）。

## 最小可用集

只跑核心功能时需要这三个（**gadget 由 `present_usb.sh` 负责，没有独立单元**）：

```bash
sudo systemctl enable --now teslausb-web teslausb-sentry teslausb-mode
```

## 常用命令

```bash
# 状态一览
systemctl list-units 'teslausb-*' 'wifi-*' --all

# 单个服务
systemctl status teslausb-web
systemctl is-active teslausb-web        # 只返回 active/inactive，脚本用

# 日志
journalctl -u teslausb-web -f            # 实时跟踪
journalctl -u teslausb-web -n 100 --no-pager
journalctl -u teslausb-sentry --since "1 hour ago"

# 重启（Web 服务建议用完整三步，见日常部署与回滚）
sudo systemctl restart teslausb-web
```

## 注意事项

**timer 是无主资产。** systemd timer 不会随代码更新自动分发，必须：

1. 加进 `deploy_manager.py` 的 `MANAGED_FILES` 白名单
2. 在常驻服务里加幂等自愈逻辑（如 `ensure_smart_switch_timers`）

否则一次清理或换机，timer 就再也不回来了（[M45](../reference/教训索引.md)）。

**dnsmasq 与 systemd-resolved 争 53 端口。** AP 场景下 dnsmasq 配 `port=0`（纯 DHCP，不做 DNS）；关闭 AP 时要删掉 `/etc/dnsmasq.d/ap.conf`（[M46](../reference/教训索引.md)）。

**「重启某个守护进程」可能等于「给整机断电」。** `teslausb-watchdog` 喂的是硬件看门狗（超时 16s）：
若它的**退出路径没有解除武装**、或**启动后有长时间不喂狗的空窗**，`systemctl restart` 就会触发硬件复位。
2026-10-15 实测：该服务原实现「未注册 SIGTERM → magic close 不执行」+「启动先等 30s 才喂狗」，
`restart` 后约 32s 整机复位（内核日志 `watchdog: watchdog0: watchdog did not stop!`）。
v0.3.1.66 已修（`install_signal_handlers()` + 先喂狗再进宽限期），但**原则不变**：
改动任何喂狗类守护进程前，先核对「停止时是否解除武装」与「启动后不喂狗的最长时长 < 硬件超时」
（[M107](../reference/教训索引.md)）。
