# 发布说明写作规范

> 适用：GitHub Release body、`CHANGELOG.md`
> 读者：准备升级的人（包括三个月后的你自己）

---

## 一句话原则

**写给人读，不写给流程看。** 升级的人只关心三件事：

1. 我该不该升？
2. 升了以后什么会变？
3. 有没有需要我手动做的事？

凡是回答不了这三个问题的内容，删掉。

---

## 读者视角：三段式结构

一个 Release body 只保留三块，按这个顺序：

| 段落 | 回答 | 篇幅 |
|------|------|------|
| **开头 2~3 句** | 这个版本整体上解决了什么，要不要手动操作 | 50 字以内 |
| **每个改动一节** | 现象 → 原因 → 现在的行为 → 对你的影响 | 每节 100~300 字 |
| **验证 / 校验** | 凭什么相信它是对的 | 3~5 行 |

不要有第四个段落。

---

## 十条禁令（AI 腔 / 翻译腔自检表）

发布前逐条对照，任一条命中就重写。

### 1. 禁「标签体」——一行一个 emoji
```diff
- 🐛 修复 UI_a112
- 🧹 udev 清理
- ✅ 审查
+ 车机不再弹 UI_a112「USB 设备故障」
+ udev 规则清理（需要手动更新一次）
```
emoji 最多在节标题里出现一次，用来标「这条要你动手」。正文里不要。

### 2. 禁「名词堆叠链」——用箭头串起来的因果
```diff
- 根因链：listdir 指纹 → drop_caches=2 → 缓存回收 → NVMe 抖动 → ep1out 禁用 → UI_a112
+ 车机写数据的同时 A7Z 在回收缓存，两次 IO 撞车，USB 端点被禁用，
+ 车机接下来的写请求排不进队，于是报 I/O 错误。
```
箭头链是**给自己看的笔记**，不是发布说明。发布说明要把箭头翻译成句子。

### 3. 禁「括号套括号」
```diff
- 修复（A1 延迟刷新）：检测到车机写入（指纹变化）→ 仅标记 dirty，不立即 drop_caches
+ 现在的做法是：检测到车机在写，先只记一个标记，不立刻动缓存。
```
一句话里最多一个括号。讲不完就拆成两句。

### 4. 禁「名词化动词」——把动作藏进名词里
```diff
- 做出相关优化调整
- 进行了修复处理
- 完成了对扫描逻辑的改造
+ 改成轮询等待
+ 删掉了 xhci-hcd 的操作
+ 加了 UDC 守卫
```
用动词开头，主语是「我们」或系统本身。

### 5. 禁「内部流程展示」
```diff
- ✅ 审查
- AI 交叉审查 6 项：4 修复（SSID 冒号解析截断、首跑基准、注释准确化、
-  rescan 旧缓存说明）+ 2 设计取舍注释化
+ 顺带修掉几个小问题：SSID 里带冒号会被截断、首次运行时的基准处理。
```
审查了几项、是谁审的、AI 还是人，跟升级的人没关系。有价值的是**改了什么**。
（如果确实需要留档，放在仓库里的提交记录或 `docs/`，别放 Release。）

### 6. 禁「免责声明体设计取舍」
```diff
- 注：nmcli wifi list 可能先返回切模式前的旧扫描缓存（非空）→ 轮询
-  提前返回旧 SSID。旧 SSID 是真实存在过的网络，_switch_to 会实际连接
-  验证，连不上则走下方"无可回连"兜底，行为正确
+ 偶尔会扫到切换前缓存里的旧网络，实际连接失败后会自动走到兜底逻辑，
+ 不影响最终结果。
```

### 7. 禁「裸数字」——数字必须带语境
```diff
- refresh_count=338
- 退避加倍（12:44:24→35）
+ 缓存回收累计触发了 338 次
+ 8 月 31 日 12:44:24 到 12:44:35 这 11 秒的日志，完整记录了一次误判
```

### 8. 禁「模板化段首」
不要每一节都用「根因」「修复」「影响」开头。同一个词在相邻三节里重复出现，
读者会自动跳过。换个说法，或者直接不写小标题。

### 9. 禁「清单尾巴」
```diff
- 附带：首跑直接刷基准、目录不可读保守刷、S3 兜底保留
```
要么单独成句讲清楚，要么删掉。塞在段落末尾的「附带：」等于没写。

### 10. 禁「机翻句式」
- 「当……时」→ 直接陈述
- 「进行了……的操作」→ 删
- 「需要注意的是」→ 直接说
- 「该问题导致了……的发生」→ 「导致了……」

## 模板

```markdown
## vX.Y.Z

一句话说清这个版本整体上做了什么。如果有需要手动操作的步骤，
在这里就点出来，别藏在文末。

### <改动标题：用用户能观察到的现象命名>

之前的现象，一到两句。

为什么会这样，用因果句讲清楚，不要用箭头链。

现在的行为是什么。

对你意味着什么（可选，只在行为有取舍时才写）。

### <需要手动操作的改动>

这条为什么不进升级包 / 为什么必须手动。

```bash
# 具体命令
```

### 验证

- 跑了什么测试，结果如何
- SHA256: `xxxxx`
```

## 命名对照

| 别这么写 | 这么写 |
|----------|--------|
| UI_a112 修复 | 车机不再弹「USB 设备故障」 |
| AP 退出修复 | 配完网后能自动回到原来的 WiFi |
| cache_coherency A1 修复 | 车机写数据时不再抢着回收缓存 |
| udev 清理 | udev 规则清理（需要手动更新一次） |
| 性能优化 | 视频列表打开快了 3 秒 |
| Bug 修复若干 | 修掉 3 个问题：…… |

判断标准：**不看代码的人能不能看懂这个标题。**

---

## 发布前检查清单

- [ ] 开头 3 秒内能看出「要不要升」+「要不要手动操作」
- [ ] 每个改动都用「现象 → 原因 → 现在」的完整句子，没有箭头链
- [ ] 全文 emoji ≤ 2 个
- [ ] 没有「根因」「修复」「附带」「注：」开头的连续段落
- [ ] 每个数字都有单位和语境
- [ ] 手动操作步骤有可直接复制的命令
- [ ] SHA256 与实际上传资产一致（见 `docs/how-to/发布新版本.md`）
- [ ] 朗读一遍，凡是读着喘不上气的长句都拆开
