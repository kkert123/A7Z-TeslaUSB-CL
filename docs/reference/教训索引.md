| M66 | **缩略图 N/A 缺格与「生成即质检」（9-5/9-6 实证）**：扫描读到的 mtime 是冻结页缓存旧值 → 误判写入已停提前生成，此刻后摄 mp4 仍在写入未封口 → ffmpeg 抽帧失败 → N/A 缺格，且缩略图已存在被永久跳过。防御：生成后校验「有视频文件的摄像头必须有帧」+ mvhd 时间匹配（M64），任一不过 → ensure_fresh(force) 重试一次 → 仍不过放弃不落盘（宁缺毋假），下轮扫描自然重试补齐。**同现象可能多根因**（旧簇串图 / 缺格 / 镜像），取证比对后再定修复 |
| M67 | **SSE stats 新增顶层字段必须同步两处摊平点（9-6 实证）**：仪表盘实时流有两条数据装配路径——SSE 首帧（system_routes stats-stream）+ broadcaster 周期帧（app_helpers），两者各自维护「顶层摊平清单」（nvme_total_disk/monthly_traffic/gpu_npu…）。新增 stats 字段只改 get_system_stats 不够，漏摊平 → 前端 `d.字段` undefined 且无报错（元素 display:none 静默不显示）。修复后用 curl 抓 SSE 首个 data 帧验证字段在顶层 |
| M68 | **oneshot 硬件初始化脚本必须可重入（9-6 实证）**：teslausb-mode（oneshot，Present 模式）重跑 usb_gadget_init.sh 时 UDC 已被上次运行的 gadget 占用 → `echo UDC > UDC` EBUSY → 服务 failed 且每次 restart 同样失败（无 Restart= 自动重试），而 gadget 实际仍在正常工作（UDC=configured）——服务状态与实况脱节。防御：绑定前检测 UDC 非空先解绑（`echo "" > UDC`）+ sleep 1，脚本可任意次重复执行；同类硬件初始化（挂载/接口/LED）都应先释放再申请 |
| M69 | **「推送断断续续」三因叠加与取证方法（9-6/9-7 实证）**：① WiFi 检测服务 `_get_current_ssid` 方法1 返回 NM 连接名而非 SSID（profile 名 WiFi-YL-MIFI-000500 ≠ SSID），同网跳过失效 + 优先级比较出 0 vs 150 幻觉 → 每 10 分钟对同一 SSID 断开重连（单日 31 次）；② 车载热点（无外网）在家可达且页面优先级最高（600），被 NM 自动选中 → 直播推送全败、仅重试队列在切回家 WiFi 的窗口零星成功；③ 重试队列 10 次/50 分钟耗尽即永久丢弃。防御：连接名→SSID 解析、优先级读页面权威值（多 profile 取 max）、位置判定落盘供独立进程共享 + 在家白名单门控、推送 10/30/60 退避、队列耗尽转每小时慢试 48 次才弃。取证关键：单事件「检测→推送」时间线逐条比对；关键词过滤会漏掉成功路径与自匹配噪音 |
| M70 | **「生成即质检」必须按目录语义设计，否则变成误杀机器（9-7 实证）**：v45 的 mvhd 串图校验拿「任一切片与事件名偏差 >300s」判定，但 SentryClips 事件文件夹天然包含触发前 ~11 分钟预缓冲切片（实测 -613s）→ 当天所有较长哨兵事件缩略图被误杀；被回收的 REC 分钟目录仍在无限重试，每轮 force drop_caches 单日 760 次 → I/O 风暴（TeslaMate/systemctl 连带超时）。防御：① 校验按目录类型区分语义——mvhd 校验仅限会被回收复用的 RecentClips；② 放弃时检测目录/前缀文件是否已消失，消失即入阻止列表（REC 平铺结构要按「event_id-*.mp4」前缀匹配，不能用 folder_path——那是基础目录恒存在）；③ force drop_caches 全局限流 60s；④ 缺格检测用目录实时列表而非抽帧前快照。另：队列 status=failed 的条目 scan 会因 seen_ids 不再入队——批量补救要清 failed 条目并重启服务 |
| M71 | **升级白名单移除文件 = 升级后版本目录缺文件（9-7 实证，连锁 M65）**：升级是「整版本目录切换」模式——脚本物理存放在版本目录内、由 /opt/radxa_data 顶层符号链接引用；v49 将 usb_gadget_init.sh 移出白名单（对齐 v48 撤销），用户升级 v50 后新目录缺文件 → 链接断链 → present_usb.sh 步骤 4 失败 → teslausb-mode failed + UDC not attached（车机存储断）。规则：**移除白名单条目前必须检查文件的引用方（symlink/ExecStart/其他脚本）；只要服务依赖，文件就必须随包分发**——哪怕内容回退为旧版。另：① deploy_manager 以 radxa 写 root 属主目录的新文件会静默失败（M65 复发），须用 sudo base64 直写；② usb-gadget.service 与 teslausb-mode 并发执行同一 gadget 脚本时互踩（一方清理删掉另一方刚建的 configfs 配置），表现为后跑者成功、先跑者 failed——排查服务失败时要先看「功能实况」是否正常（UDC=configured），再查状态 |
| M72 | **中断会话恢复与发布后核验的官方姿势（9-10 实证）**：① 跨会话/中断恢复前先核实真实状态——查 `git log` HEAD 与 `.workbuddy/artifacts/` 产物时间戳。本次被打断的命令里 commit+构建+签名实际都已完成，只缺 push+Release；若按对话摘要「未提交」重做，等于白干并可能覆盖已签名产物；② `ssh-keygen -Y verify` 的 allowed_signers 行格式是 `principal keytype base64`（principal 在前），顺序写反会报 "Could not verify signature"（是格式错，不是签名坏了）；③ 资产 SHA 核验不必下载（github.com 直链可能被阻断，M48 场景）——`GET /releases/assets/{id}` 的 `digest` 字段就是 GitHub 服务端算的 sha256，与本地 `sha256sum`、body 声明三方比对即可；④ 设备实际版本以 `/api/version/check` 的 `current` 字段为准，不能按 `/releases/latest` 假定（本次设备实为 v52、无 v53 安装痕迹，另案待查） |
| M74 | **同一份 gadget 脚本被两个 systemd 单元开机并发执行 → 抢绑同一 UDC（9-12 事故 / v0.3.1.55 修复）**：① 现象——车机哨兵录制中途瞬断、偶发直接退出哨兵（内核 `dwc3 6a00000.xhci2-controller: ep1out: can't queue to disabled endpoint`）。根因**不是脚本内容**，而是「两个 owner」：设备侧历史遗留 `/etc/systemd/system/usb-gadget.service`（enabled、oneshot、`After=network.target`）与 `teslausb-mode.service`→`present_usb.sh` 开机都执行同一份 `/opt/radxa_data/usb_gadget_init.sh`（顶层符号链接→版本目录），谁后绑谁挤掉先绑。② 触发器：v0.3.1.51 把该脚本重新装回版本目录，修复了 7-8 创建的**悬空符号链接**——这个此前 `status=127` 一直启动失败的遗留服务**从「起不来」变成「真跑起来」**；改动本身没碰服务，却激活了沉睡的第二个 owner。③ 防御：升级后置钩子 `_disable_legacy_gadget_service()` 停用该遗留单元（**只 disable 不加 `--now`**——其 ExecStop 是 `usb_gadget_init.sh stop`，会解绑 gadget、卸载分区，拆掉当前车机存储）；脚本加 flock 全局互斥（fail-open，防并发抢绑）；修正 M68 的 UDC 已绑定判定（`[ -s UDC ]` 把 1 字节换行误判为已绑定 → 改 `tr -d '[:space:]'` 后判非空）。④ 排查手法：`systemctl cat <unit>` 看 ExecStart 指向、`readlink -f` 看符号链接指向、`journalctl -u A -u B` 看两单元执行时间线 |
| M75 | **「升级后置钩子」有自举缺口：它在旧版本进程里执行，永远滞后一个版本（9-14 实证 / v0.3.1.56 修复）**：`do_upgrade()` 运行在**当前进程 = 升级前那份代码**里，新钩子函数只存在于新版本代码中——从 <v55 直接升到 v55+ 时，运行的程序里根本没有这段新代码，停用逻辑被跳过（设备实测：v54→v55 升级后 `usb-gadget.service` 仍 `enabled`）。**凡「升级后置钩子」皆有此共性缺陷**，只有「已装新版再升级」才轮到它执行。防御：把关键后置动作搬到**启动期幂等自愈**——`app.py` 启动块起 daemon 线程（延迟 15s，不阻塞 Web）调 `upgrade_service.startup_self_heal()`，每次 boot 检查 legacy 单元，`enabled` 即 `disable`（两分支均实测：已被钩子停用→「无…需处理」；手动 enable 后重启→「已停用…」）。口诀：**要覆盖所有升级/重装/回滚路径，必须有启动期兜底，不能只靠后置钩子** |
| M76 | **Release body 的 SHA256 行禁止任何包裹符号（9-14 事故 / v0.3.1.56 修复）**：设备端 `version_service` 用正则 `(?:SHA-?256|sha256)[:\s]+([a-fA-F0-9]{64})` 从 release body 提取校验码，要求冒号后**紧跟 64 位 hex**。发布说明规范的模板曾写作带反引号的 `` - SHA256: `xxxxx` ``，照抄后一个反引号挡在 hex 前 → 解析失配 → `sha256=''` → 前端 `if (!body.sha256)` 直接报「发布页未找到 SHA-256 校验码，升级中止」。防御：模板改纯文本 `SHA256: <64hex>`、规范加硬约束+检查清单项、发版脚本内置上线前自检与发布后正文回读复核。教训：**照抄文档模板前先核对下游解析器** |
