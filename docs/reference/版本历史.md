## v0.3.1.65 · 2026-10-14（**构建中**）

### 修复：网络卡片「本月家庭WiFi / 本月车辆热点」两栏归属反了

- **现象（用户报告）**：网络卡片显示「本月家庭WiFi ↓4.29GB ↑1.97GB / 本月车辆热点 ↓20.3MB ↑15.77MB」，而设备大部分时间在车里、只有在家才连家庭 WiFi —— 两栏实际是反的。
- **根因（M105）**：`utils/traffic_monitor._current_category()` 只问「A7Z 自己的 AP（hostapd）是否激活」：`"hotspot" if _ap_active() else "home_wifi"`。于是**车里连着车载热点**（STA 联网、自己 AP 关着）这一**主流量场景**被归进 `home_wifi`。真机证据：当前 wlan0 关联 `YL-MIFI-000500`（车载热点），而本月 `home_wifi` ↓4.61GB↑2.13GB、`hotspot` 仅 ↓21MB↑16.5MB；9 月 `home_wifi` tx=**45.4GB**（大额云上传都发生在车里走 MIFI）。
- **修复**：按**当前连的是哪个网络**分类 —— ① 命中 `home_wifi_ssids` → `home_wifi`；② 命中 `hotspot_ssids` → `hotspot`；③ 确知连着一个两列表都没列出的网络 → `other`（页面**单列**、仅非零时显示，不再是看不见的黑洞）；④ 自己在当 AP → `hotspot`；⑤ 两列表都没配置 → **完整回退旧行为**（不退化成两栏全 0）。
- **新增 `utils/ssid_match.py`**：SSID / NM 连接名匹配的**唯一权威实现**（`norm`/`strip_wifi_prefix`/`as_list`/`matches`），同时比对 SSID 与连接名、容忍 `WiFi-` 前缀差异。**顺带修活** `location_detector` 从上线起一直静默失效的「连热点=外出」WiFi 辅助判定（配置存的是 **NM 连接名**，而代码比较的是**裸 SSID**，`in` 永不相等 → 只影响 confidence/来源标记，不影响 state，故此前未被发现）；并把它的 `set(...)` 改成**保留顺序的 list**——原 `list(set)[0]` 被当作"待切换的 SSID"传给 `switch_wifi()`，取值随 `PYTHONHASHSEED` 漂移、可能拿到连接名而非 SSID。
- **审查加固（交叉审查发现，均已修）**：① 分类计算**移出 `_lock`**——原在锁内会起 nmcli/systemctl 子进程（最坏合计十几秒），连带阻塞共用同一把非重入锁的 `get_monthly()`（页面与 SSE 渲染）；② 探测/配置读失败时**保留上一份有效值**、不写空覆盖（否则一次 nmcli 抖动或配置非原子写被读到半截，就让随后 60s 的流量全落进不可见桶，表现成"统计整个坏掉"，比旧的"数字反了"更难查）；③ `_current_category()` 加上兜底，**保证不抛**；④ 异常捕获由 `(OSError, ValueError)` 放宽到 `Exception`，配置项类型规整（str 按逗号拆；**绝不 `tuple("abc")` 退化成字符元组**）。
- **设备侧**：`hotspot_ssids` 补入裸 SSID `YL-MIFI-000500`（原只有连接名 `WiFi-YL-MIFI-000500`）。升级会**保留设备 `config/`**（`upgrade_service._restore_user_data`），不会被包内的空模板覆盖。
- **历史数据不回填**：本月已混在一起的流量无法回溯拆分；`other` 亦从本月起才有意义。

- **已验证**：`_test_traffic_category.py` **30/30**（T 组决策表 14 项、W 组 `_wifi_context()` 本体 7 项【专治原测试把该层整个桩掉的盲区】、S 组共用匹配 10 项）；`_test_cleanup_guard.py` 36/36、`_test_usbguard_editgate.py` 15/15 复跑通过；`py_compile` + `dashboard.html` 内联 JS `node --check` 通过。

## v0.3.1.64 · 2026-10-14（**已发布** Release ID 412795862 / tag→`2ea6214`；真机已升级并验证）

- **现象（用户报告）**：v0.3.1.63 装好后，**切到 Edit 模式直接点「立即执行清理」仍然报错**——单次 **4080 条** `删除失败 …: [Errno 30] Read-only file system`、`❌ 清理未生效: 计划删除 4080 个文件，实际删除 0 个`；必须先点一次「预览清理」再执行才正常。
- **根因（M103）**：**不是清理代码，是 `usb_guard` 在"抢模式"**。它的健康判据是「线在位 + UDC `state=='configured'`」（M80），无模式感知；Edit 下 gadget 是**故意**解绑的而车机线还插着 → 判为链路卡死 → 30s 后 L2 = `usb_gadget_init.sh restart` → 其 `remount_all_ro()` **把 cam 强制打回只读 + 重新绑 gadget**。journal 铁证：`21:03:12 stop(切Edit) → 21:03:16 switch 200 → 21:03:52 execute（remount rw 成功、清掉 560MB 缩略图，即历史里 freed=560.3MB）→ 21:03:58 [USBGuard] L2 结果：成功 — usb_gadget_init.sh restart → 21:04:21 start` → 删除循环开始时分区已只读。用户"先预览"的手法其实是**耗掉本次故障期的一次性 L2**（M80：同故障期内各级最多一次、恢复即清零），之后 remount 才不被推翻。附带副作用：切 Edit 后约 30s gadget 被擅自绑回 Present，而 `/tmp/teslausb_mode` 仍是 `edit`。
- **修复（三处复合成一招）**：① `usb_guard.py` 新增 `intended_mode()` + `tick()` 的 **Edit 模式闸**：`/tmp/teslausb_mode=='edit'` 时「线在位但 UDC 未配置」按预期处理，不进故障期、不动作，并把已累计故障期清零（phase 记 `edit_mode`）；标志读不到 → 维持原行为（fail-open，不削弱 M80）。② `usb_gadget_init.sh` 的 `start`/`stop` 也写 `/tmp/teslausb_mode`（present/edit），让标志始终反映**真实意图**——`auto_present_service` 走 `start` 切回 Present 时不写标志会留下 stale `edit`，反而挡住真实自愈。③ `routes/cleanup_routes.py` 把「确认 cam 可写」从入口挪到**紧邻视频删除之前**，并新增 `_ensure_cam_writable()` 用**真实写探针**（create+remove `.wb_write_probe`）作最终判据；失败即 409 中止，不再产生成千上万条 EROFS。
- **已验证**：`py_compile` + `bash -n usb_gadget_init.sh` 通过；新增 `_test_usbguard_editgate.py` **15/15**（Edit 不进故障期 / present 仍进故障期 / 标志缺失 fail-open / Edit 闸清零已累计故障期 / 拔线不动作 / 脚本写标志），`_test_cleanup_guard.py` 扩到 **36/36**（W 组专测 `_ensure_cam_writable`：rw 直通、ro→remount→探针通过、目录不可写→False、未挂载→False、端点遇不可写 409 且未删视频）。
- **已发布**：commit `2ea6214`（6 文件）→ Release **ID 412795862**（`teslausb-v0.3.1.64.tar.gz` 541201 B / `.sig` 294 B，`target_commitish=master`）。三方核对全绿：tag→`2ea6214`｜asset digest `sha256:acd39bbf…` == 本地 == body｜body SHA256 行正则通过；本地 `ssh-keygen -Y verify` 通过。M41/M33/M84 均通过（仍仅差既有运行时 `config.json`）。
- **升级踩坑（新）**：经 Web 一键升级（URL 下载路径）**连续两次 stall 在下载步骤**（ghproxy 首源 300s 超时 + 直连 GitHub 极慢），第一次在 ~5min 后以**空响应**结束并留下了 **stale 的 `/var/run/upgrade_progress.json`（12%）**——页面因此一直显示"升级中"，而实际版本没变、进程重启后无升级线程存活。**处置**：清理 stale 进度与残包后，改用 `POST /api/version/upgrade-upload`（本地上传 541KB 包，走 Tailscale 秒级完成）→ 备份 + 安装 + 切 symlink + 重启一次成功。**待办**：这属于"URL 下载路径在本网络下不可靠"，可考虑把 web 页一键升级默认改为「先上传本地包」或给 download 加更小的 timeout + 更早的镜像降级。
- **真机验证（10-14，设备已升至 0.3.1.64；web 22:19:05 / usb-guard 22:19:24 均已加载新代码）**：
  - **USBGuard 不再偷模式**：切到 Edit 后 **t+0 / t+75s**（远超 L2 的 30s 窗口）均为 `mode=edit`、**UDC 仍"(无)"**、`cam=ro`；`/opt/radxa_data/teslausb/data/usb_guard_status.json` → **`phase=edit_mode`、`stages=[]`**（旧版此处必然已 `restart` 并重绑 UDC）。
  - **Edit 下 execute 全链路通**（不删数据做法：临时把三个文件夹策略 `enabled` 全置 false → 计划为空 → 跑 execute → 立刻还原并复核）：`HTTP 200 / success=True / deleted_count=0`，输出 `🔓 检测到只读挂载，正在 remount 读写... → ✅ cam 分区可写（写探针通过） → ℹ 没有需要清理的视频文件`；策略逐字段还原（`enabled` 全部回到 true）；`preview` 计划仍为 **4080 个 / 112.15 GB**（录像完好无损）。
  - **注意**：若不在 Edit 窗口内执行（超过 AutoPresent 的 **2 分钟**倒计时，模式已自动切回 Present），execute 会（正确地）返回 409 并提示"USB Gadget 已独占块设备"——本次验证第一次就是这样被拦下的，恰好反证了守卫在工作。
- **⚠ 遗留（新发现，待决策）**：**Edit 窗口只有 2 分钟**（`auto_present_service` 倒计时），而真实清理 4080 个文件 / 112GB 很可能超出该窗口 → 倒计时到点会 `usb_gadget_init.sh start`，其中 `umount` + 重绑 gadget 会在清理中途把分区打回只读甚至与清除并发（即 **M102** 那条竞态的实锤）。建议：清理期间**取消/推迟** auto-present 倒计时、结束后再恢复。
- **⚠ 遗留（新发现，待决策）**：`start_gadget` 的 `remount_all_ro()` 对被清成 **rw** 的 cam 无法收回 ro——它用 `mount -o ro <dev> <mp>`（目标已挂载 → 失败）而不是 `mount -o remount,ro`，且此时设备已被 gadget 占用；实测切回 Present 后 `cam` 仍为 `rw`（本次已手工 `remount,ro` 复原）。建议把 `remount_all_ro` 里"已挂载但不是 ro"的分支改为 `mount -o remount,ro "$mp"`（教训 **M104**）。

## v0.3.1.63 · 2026-10-14（**已发布** Release ID 412657955 / tag→`ba5420d`；真机已升级并验证）

- **现象（用户报告）**：`/analytics` 页直接点「⚡ 立即执行清理」报错，必须「切换模式→预览清理→立即执行清理→切换回模式」才成功。用户给出的日志时间戳 `2026/10/11 06:12:21` 是**页面「清理历史」用 `toLocaleString('zh-CN')` 渲染出的格式**（斜杠日期），对应设备 `cleanup_history.json` 的 `2026-10-11T06:12:21.126657`：`deleted_files=0`、`errors=4437` 条，**4437 条全是** `删除失败 /mnt/teslacam/TeslaCam/...: [Errno 30] Read-only file system`。同现象 09-30 22:46 亦复现（4160 条）。
- **根因（M100 + M101）**：Present 模式下 Tesla 通过 USB Gadget 独占 `/dev/nvme0n1p2`，A7Z 侧只能只读挂载（`present_usb.sh` 直挂 ro，失败退化为 `losetup -r` **只读回环**）→ `api_cleanup_execute` 里的 `mount -o remount,rw` **不可能成功**；而旧实现**不检查 returncode**、二次校验结果丢弃、还**无条件**打印「✅ 已切换为读写模式」，随后照常 `os.remove()` → 每个文件 EROFS。切到 Edit 模式后 gadget 解绑、块设备空闲，同一句 remount 才生效 —— 这就是「必须先切模式」的原因。
- **方案 A 落地**：
  - **统一模式探测**（`routes/cleanup_routes.py` 新增 `_read_cam_mount()` / `_gadget_bound()` / `_is_loop_source()` / `_detect_cam_mode()`）：Present 判据 = **gadget 已绑 UDC（判「内容非空」，configfs 里解绑后文件仍在）或挂载源是只读 `/dev/loop*`**；编辑模式的 ro 直挂判为 `edit`（M100）。`/api/cleanup/status` 新增 `mode`，preview 改用同一探测。
  - **Present 前置守卫**：命中即**不做任何删除**（含预览图/日志等非视频清理），返回 **409 + `success:false`** 并给出原因与「请切到 Edit 模式」；前端据 `mode` 禁用执行按钮 + 给一键「切换到 Edit 模式」入口（带 U 盘短暂断开的确认）。
  - **remount 兜底重写**：逐条记录 `returncode`、每条后重读 `/proc/mounts` 复核；两次都失败 → 409 中止且零删除；成功日志只在复核通过后打印。
  - **失败语义**：有计划但**实际删除 0 个视频** → `success:false`（HTTP 500）；计划内文件**全部 missing** → 视为已达成，`success:true`；只删一部分 → `success:true` + `partial:true` + 提示。分子改用 `breakdown` 的**计划内视频数**（`deleted_files` 含 event.json/thumb.png 孤儿文件，会算错 partial）。
  - **历史与前端**：一次执行只写**一条**历史（`execute_cleanup(plan, save_history=False)`，此前 route + AutoCleaner 各写一条）；历史补 `errors/error_count/actions/partial`；`/api/cleanup/history` 把 `errors` 裁剪为前 5 条 + `error_count`（旧条目单条 4437 条 → 响应体 2MB，会把页面撑爆），并容忍 `errors` 为 str/dict、非 dict 条目；前端渲染 errors 并统一 `esc()` 转义（错误文本含文件路径，走 `innerHTML`）。
  - **顺带修**：`auto_cleanup.run()` 删除计数**翻倍**（`result is self.stats` 后又 `+= result[...]`）+ 重复写历史；非视频阶段的 errors/actions 被 `execute_cleanup` 重置 stats 后丢弃；「保留当前 + 4 历史」文案与 `keep=2` 不符。
  - **判据收敛为唯一实现**（`utils/system_info.py` 新增 `read_cam_mount`/`gadget_bound`/`is_loop_source`/`detect_cam_mode`）：`routes/cleanup_routes.py` 改为导入（保留同名私有别名），并**一并修** `/api/mode/status` 的兜底探测（`routes/misc_routes.py`）——该分支原有两处错：① gadget 目录名**硬编码 `g1`**（实际 `tesla_usb`）→ 判据恒 False；② 拿「cam 以 ro 挂载」当 Present 判据 → 把 Edit 误报成 Present（与本次主缺陷同源）。平时走 `/tmp/teslausb_mode` 不触发，只在 flag 丢失时误报模式。
- **双审查**：第一轮交叉审查抓出**致命回归 S1**（初版判据 `is_ro` 会把 Edit 模式一起拒掉，并使 remount 块成死代码）→ 改判据；第二轮抓出 `partial` 口径错位（孤儿文件）、`run()` actions 重复、前端数值字段未转义等，均已修。
